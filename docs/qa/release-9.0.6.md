# 9.0.6 — производительность сортировки и «Инфо»

17.11.2026, ветка `codex/performance-9.0.6`, отдельная рабочая копия. Исходная папка пользователя не изменена.

## Исправление

В 9.0.5 каждый успешный пакет фоновой сверки считался изменением. Даже одинаковые данные запускали гидратацию обоих каталогов, полный пересчёт правил, отрисовку папок и следующий полный пересчёт. Теперь метаданные сравниваются отдельно от отметки свежести. Неизменившийся пакет обновляет свежесть и продолжает сверку без этой работы. Реальное изменение сохраняет прежний путь применения.

Идентификатор аккаунта и контекст native-счётчиков определяются один раз в синхронном проходе. Контекст не кэшируется между событиями. Запись идентичного каталога в localStorage пропускается после существующего трёхстороннего объединения.

Правила, приоритеты, ручное подтверждение, исключения, период сверки, объём пакета и защита от старых ответов не изменены. Во вкладке «Инфо» описаны эти правила и пример смены исполнителя. Переключение вкладок сохраняет черновик.

## Методика

`tests/automation-performance-regression.mjs`: полный runtime в Chromium, 4000 задач, 12 правил; 14 секунд активации/сверки, 12 секунд неизменившейся сверки, 10 кликов реальных кнопок папок. CDP Performance/CPU profiler, event-loop latency, long tasks, вызовы пересчёта/отрисовки, число API-запросов, объём записей. Обе версии запускаются последовательно на одном компьютере, без параллельных тяжёлых тестов. В отчёте указан SHA-256 runtime.

Диагностический сборщик визуального стенда (каждые 5 мс) отключён в обеих версиях: его сериализация не является работой расширения. Известные задачи имеют согласованные ответы list/get/dialog.get; проверяются итоговые папки и канонические названия. Ранние исследовательские замеры со сборщиком или неполной моделью API не служат доказательством скорости релиза.

Это измерение работы главного потока на стенде, а не CPU всего компьютера, памяти или живого пользовательского портала. Старый microbenchmark `render-performance-regression` сравнивает с 8.0.66 и не используется для обещаний ускорения относительно 9.0.5.

| Сценарий | JavaScript 9.0.5 → 9.0.6, мс | Главный поток 9.0.5 → 9.0.6, мс |
|---|---:|---:|
| Активация и сверка | 518.36 → 123.05 | 960.32 → 208.80 |
| Неизменившаяся сверка | 438.23 → 24.17 | 831.58 → 68.36 |
| 10 кликов папок | 484.91 → 287.67 | 669.08 → 385.11 |
| Сумма сценария | 1441.50 → 434.88 (3.31×) | 2460.98 → 662.28 (3.72×) |

За тихие 12 секунд API продолжал работать: 11 запросов до, 12 после; пересчётов правил 46 → 0, гидратаций 11 → 0, перерисовок панели 22 → 0. Это не замедление сверки ради меньшей нагрузки. В сценарии кликов выигрыш скромнее (~1.7×), поэтому трёхкратный результат относится к суммарному сценарию, а не к каждому действию. Ускорение ОЗУ/компьютера в целом не заявляется.

Повтор той же пары после заморозки runtime: JavaScript 1831.31 → 441.48 мс (4.15×), главный поток 3304.78 → 659.66 мс (5.01×). Консервативный заявленный результат берётся из первой, менее выгодной пары: 3.31× / 3.72×. Обе пары и одинаковые SHA-256 сохранены в JSON.

- `rules-live`: 13 сценариев, включая пропущенный Pull, новый диалог, все изменяемые поля, гонку ответа, offline/backoff и ручное подтверждение.
- `rules-settings-ui`: справка на 1100 и 390 px, сохранение черновика, обязательные условия, переключение автоподтверждения и пакетные действия.
- `read-state`: 19 функциональных сценариев; актуальность native-счётчиков при повторных проходах сохранена.
- `rules-required-transfer-model`, `rules-priority`, `rules-resorting`, `native-switcher-filter`, `render-performance`, `release-integrity`: PASS до заморозки.
- Релизная проверка: точный search-focused 16, прежние дополнительные gates и новая проверка отсутствия лишних пересчётов при действующей фоновой сверке. Статус публикации фиксируется после завершения CI и доставки.

Физический Mac и пользовательская вкладка Chrome не проверялись. Native Computer Use не использовался.

- Планирование сверки останавливается на первом просроченном кандидате; пакет в момент запроса строится заново. Нагрузка уменьшена без удлинения интервала сверки и backoff.
