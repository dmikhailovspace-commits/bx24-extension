# Загрузка времени и повторные контакты — 7.5.100

## Причина постоянной загрузки

В v7.5.99 проверка времени считала снимок задачи устаревшим через 10 секунд при наличии записей и через 120 секунд без записей. Полный обход большого каталога занимал больше этого срока. Начало списка устаревало до проверки хвоста; очередная проверка каталога, повторное открытие и даже завершающая часть ручного обновления запускали новый обход.

Независимый стенд использует реальные функции загрузки и модель данных с 4149 задачами и виртуальной задержкой 2 секунды на batch. Первый проход: 84 batch, 168 виртуальных секунд. Это модель задержек, а не измерение пользовательского портала.

| Действие после первого прохода | v7.5.99: запросов записей задач | Новая политика |
|---|---:|---:|
| Повторное открытие периода | 1216 | 0 |
| Три сигнала проверки без изменений | 5017 | 0 |
| Изменилась одна задача | 4149 | 1 |
| Два одновременных ручных обновления | 5365 | 4149 |
| Ручное обновление во время первого прохода | 8298 | 4149 |

## Когда выполняется чтение

- Первый просмотр ещё не загруженного периода последовательно проверяет все известные задачи. Первые полезные суммы появляются после приоритетной волны, полнота отмечается отдельно.
- Подтверждённый снимок не теряет силу только из-за возраста. Повторное открытие использует его. Событие задачи, новая дата изменения, собственная запись и квалифицированный контакт дают повод проверить конкретную задачу.
- Открытая панель продолжает короткую проверку изменений каталога по `CHANGED_DATE`. Неизменившийся ответ не запускает чтение записей времени. Закрытая панель только запоминает инвалидацию; сетевое чтение откладывается до открытия.
- Ручная кнопка проверяет весь выбранный период. Одновременные клики объединяются; нажатие во время первоначального прохода присоединяется к нему. События, пришедшие во время чтения, добираются одним объединённым проходом только по изменённым задачам.
- Недоступная задача не считается проверенной пустой. Последние данные и сообщение об ошибке сохраняются; повтор возможен по ручному действию, изменению задачи или новому квалифицированному контакту.

Кеш хранится в памяти документа и содержит до восьми периодов. После перезапуска Bitrix или вытеснения периода его первоначальный проход повторяется. Глобальное чтение времени всех задач одним вызовом не используется: официальный метод возвращает записи конкретной задачи. [Документация task.elapseditem.getlist](https://apidocs.bitrix24.com/api-reference/tasks/elapsed-item/task-elapsed-item-get-list.html).

Отдельной документированной гарантии события для любого внешнего изменения записи времени нет. Изменения из расширения отражаются после ACK; внешние изменения подхватываются событиями задач, дельтой каталога и точечной проверкой при работе с задачей. Ручное обновление остаётся способом полной сверки. [События задач](https://apidocs.bitrix24.com/api-reference/tasks/events-tasks/index.html).

## Статус загрузки

Строка видна при первоначальном неполном чтении, ручной проверке и ошибке. Подтверждённый полный снимок сохраняется на экране при точечном фоновом чтении; строка в это время скрыта. Если реально изменилось больше одного пакета задач (50), появляется «Обновляем изменённые задачи» с прогрессом. Неизвестный итог обозначается прочерком. Реальный ноль остаётся нулём. Тесты различают подтверждение отдельных значений и завершение полного первоначального снимка.

## Контакты после внесённого времени

Контакт не является предложением длительности. Пользователь сам вводит дополнительное время.

1. До внесения карточка показывает число ожидающих квалифицированных контактов.
2. Успешное внесение учитывает только контакты до отправки этой записи. Карточка уходит из ожидающих, если новых контактов нет.
3. Новая активность возвращает карточку с контекстом: «Учтено 30 мин · +2 контакта после записи». Число относится к новым контактам, сумма — к уже внесённому времени выбранного дня.
4. Контакт, возникший во время ответа сервера или сохранения локального журнала, остаётся ожидающим. Отказ или неизвестный исход записи не снимает контакты.
5. Изменение длительности или удаление записи обновляет сумму; оно не поглощает новые контакты и не возвращает уже учтённые.

`CREATED_DATE` определяет рабочий день, но не момент фактического внесения: ручная запись может быть датирована полуднем или прошлым днём. Для внешней записи используется явный `DATE_START` с часовым поясом. Для записи расширения приоритет имеет её подтверждённый ID и неизменяемая граница контактов на момент отправки. Если надёжного времени внешнего внесения нет, контакты сохраняются. [Поля записей времени](https://apidocs.bitrix24.com/api-reference/tasks/elapsed-item/task-elapsed-item-get-list.html).

## Проверки и ограничения

После подтверждения ADD с ID сохраняется отдельное состояние `acknowledged` и неизменяемая граница контактов. Если журнал контактов временно не записался, повтор восстанавливает только отметку: новую запись времени не отправляет. Отложенные сохранённые сегменты таймера также восстанавливают только журнал. Ошибка этой вспомогательной операции не превращает успешно сохранённое время в ошибку ADD. При полном отказе всех локальных записей и аварийном перезапуске до сохранения ACK восстановить его ID гарантированно нельзя: прежнее `sending` становится `unknown`, автоматического повтора ADD нет.

- `time-large-catalog-acceptance.mjs`: большой каталог, отсутствие циклов, точечные изменения, объединение ручных запросов, смена пользователя, закрытие и события во время чтения.
- `time-panel-feedback-regression.mjs`: настоящий Chromium и управляемые ответы SDK; первоначальная неполнота, скрытая фоновая проверка, ручное обновление и ошибки. Браузерный стенд содержит 30 задач; он не выдаётся за браузерный замер 4149 задач.
- `time-contact-followup-regression.mjs`: остаток контактов, запоздалый outbox, дедупликация, старые журналы, границы подтверждённых записей и внешние даты.
- `time-contact-cutoff-acceptance.mjs`: независимая проверка границ контактов, поздних событий и ответов сервера.
- `time-contact-ack-acceptance.mjs`: настоящий Chromium, удержанный ADD, отказ записи журнала, перечитывание сервера, перезапуск и повторные нажатия. Подтверждает один ADD, сохранённую сумму и новый ожидающий контакт. Снимки карточек проверяются при 344 и 720 px.
- Остальные функциональные наборы проверяют сохранение, восстановление, межоконные блокировки, время и нативный интерфейс. Результат полного релизного прогона фиксируется в `tests/artifacts/regression-summary.json` и provenance-файле релиза.

Живой пользовательский портал и физический Mac этими стендами не проверяются. Скорость первого серверного ответа зависит от Bitrix; устранён повтор уже завершённой работы, а не заявлена мгновенная проверка всего портала.
