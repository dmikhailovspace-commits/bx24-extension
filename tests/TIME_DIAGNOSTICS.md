# Проверки панели времени

Полный прогон: `pnpm test`. Итоги появляются в `tests/artifacts/regression-summary.json`: результат, длительность каждого набора и пять самых долгих. Ошибка любого набора завершает прогон с ненулевым кодом. Полный вывод сохраняйте отдельно, например `pnpm test *> tests/artifacts/full-regression.log`.

Панель отдельно: `node tests/time-functional-regression.mjs` и `node tests/time-panel-layout-regression.mjs` на Node 20+. Функциональный отчёт — `tests/artifacts/time-functional-report.json`, снимок — `tests/artifacts/time-panel-current.png`. Проверки запускают настоящий Chromium на локальном стенде с подменённым Bitrix API. Это не замеры задержки живого портала.

## Что проверяется

- Иконки, размеры и центровка; адаптивные ширины 1280/768/681/680/420/360.
- Панель поверх сторонней плашки с максимальным z-index и внутри трансформированного родителя; сводка уходит при прокрутке.
- Поиск задачи с учётом времени без CHAT_ID; исключение явного N; актуализация Y/N по событию задачи.
- Каталог из 125 задач: ID-keyset с >ID и start=0 на каждой странице, доступность последней подходящей задачи, следующий проход только по CHANGED_DATE. task-keyset-regression отдельно проверяет удаление между страницами, игнорирование фильтра сервером и смену scope.
- Смена запроса во время проверки 80 задач с неизвестной eligibility: старый поиск не запускает оставшуюся цепочку запросов.
- Скрытая вкладка не добирает 60 секунд до контакта; перед квалификацией заново проверяются и устаревшее Y, и устаревшее N.
- Редактирование записи во время незавершённого чтения: задержанный старый ответ не заменяет итог после сохранения; после него выполняется одно объединённое повторное чтение.
- Общий набор run-native-regressions проверяет ручное добавление, редактирование даты/длительности, удаление, запуск/остановку/отмену таймера, ошибки API, входящие/исходящие сообщения и межфреймовый lease.
- Отдельные cold-task-interaction и message-performance проверяют клики, ввод и обработку уже полученных событий: MutationObserver, REST-вызовы, storage, длинные задачи браузера и скачки кадров. Первая проверка намеренно исключает стартовую materialization; эти два набора не измеряют сетевое завершение отправки сообщения.
- `interaction-contention-regression.mjs` сравнивает включённое и выключенное расширение: trusted click → настоящий HTTP-запрос → следующий кадр. Одинаковый стенд с четырьмя серверными слотами, CPU ×4, 4000 элементов истории и 120 заменами каждые 100 мс работает во время старта и после завершения загрузки. `acceptance-audit-current.json` содержит median/p95/max, long tasks, frame gaps, observer CPU, очередь сервера и ошибки. Это модель общей нагрузки, не копия сервера Bitrix.
- В каждом плече выполняются ровно 24 завершённых действия на фазу. Отдельные бюджеты для старта и обычной работы сохраняют абсолютные пределы 300 мс HTTP / 350 мс до кадра либо удвоенный p95 выключенного плеча, если он больше. Нагрузочный тест не запускает наследованный от recovery-стенда опрос `sampleGuard` каждые 16 мс: тот принудительно читал геометрию всей страницы и искажал профиль. Основные recovery-тесты сохраняют этот sampler для проверки визуального guard.
- `network-idle-regression.mjs` проверяет 100 событий задач при закрытой панели, свежую проверку перед контактом, объединение событий открытой панели и отмену запросов после скрытия. `native-batch-backpressure.mjs` запрещает повтор пачки из 50 чтений после таймаута/лимита, сохраняет частичные ответы и проверяет запрет повторов записывающих методов.
- `native-dom-mutation-regression.mjs` проверяет повторное применение оформления 1000 настоящих строк: количество мутаций, сохранение ID, scrollbar и нативного typing overlay. Снижение MutationRecords не равно такому же ускорению всего интерфейса.

## Диагностика в открытом Bitrix

В консоли frame, который содержит Messenger:

```js
const report = window.__PENA_REST_DIAGNOSTICS__?.snapshot();
console.table(report?.samples);
```

`queuedMs` — ожидание собственной очереди расширения; `durationMs` — время от отправки в SDK до ответа; `status/code` — результат. `active`, `queued`, `peak`, `deduplicated` показывают текущую нагрузку и объединённые чтения. Хранятся последние 200 измерений в памяти, без параметров, токенов, названий задач и сообщений. Batch помечен именем вложенного метода; длительности отдельных подзапросов SDK не предоставляет. Сводный отчёт содержит SHA-256 проверенного runtime и обновляется после каждого набора, чтобы незавершённый прогон нельзя было принять за старый успешный. `native-scenarios.json` разбивает большой нативный набор по URL сценариев и сохраняет REST-метрики каждого; длительность сценария включает заданные тестом ожидания и не равна времени загрузки страницы. Ошибки recent-sync сохраняют состояние в `recent-failure-*.json`. При падении loading-race состояние каталога, вызовы и очередь сохраняются в `tests/artifacts/loading-race-failure.json`.

Устойчивая интенсивность ограничена двумя запросами в секунду, параллельность — двумя; начальный запас — 16 запросов с интервалом не меньше 80 мс. Таймаут/ограничение API дают паузу 15 секунд. Уже отправленный SDK-запрос физически отменить нельзя: его поздний ответ не применяет устаревшее состояние. Это локальная очередь экземпляра Messenger, а не общий лимит всех открытых приложений пользователя.

## Как считаются контакты

Контакт — квалифицированное обращение к задаче с подтверждённым `ALLOW_TIME_TRACKING=Y`: 60 секунд видимого просмотра или подтверждённое исходящее сообщение текущего пользователя в её чате. Быстрый просмотр, входящее сообщение и обычный чат не учитываются. Повторные события внутри 15 секунд объединяются моделью контактов. Сообщение уже квалифицирует текущее обращение: последующее достижение минуты не должно добавлять второй контакт. Скрытие приостанавливает отсчёт; смена задачи/режима и закрытие задачи завершают просмотр. Перед записью квалифицированного контакта флаг проверяется повторно, даже если в кеше уже есть Y или N: это закрывает потерянное событие переключения. Ошибка проверки eligibility не превращается в N, контакт остаётся в очереди повторной проверки.

Контакт сам по себе не записывает рабочие минуты. Длительность задаёт пользователь или явный таймер.

Квалифицированное событие сохраняет исходный момент, пользователя и уникальный ID в отдельном ключе локального outbox. Поздний retry не переносит контакт на сегодняшний день. Если часовой пояс портала ещё неизвестен, дата ждёт объединённого `server.time`, а событие сохраняется; ошибки сети не подменяют часовой пояс настройкой компьютера.

Все изменения дневного журнала проходят один Web Lock и читают актуальную запись внутри него. ID обработанного события сохраняется вместе с контактом до удаления outbox: повтор после сбоя подтверждения не создаёт дубль. Старый снимок другого окна не перезаписывает новые контакты. Для межоконной записи нужен безопасный контекст с Web Locks (HTTPS в актуальном Bitrix Desktop). При недоступности механизма событие остаётся в очереди; диагностика показывает `CONTACT_STORAGE_LOCK_UNAVAILABLE`.

`time-contact-journal-regression.mjs` проверяет быстрые A→B→A, сообщение во время ожидания API, более 40 задач, ночь и другой часовой пояс, отказ storage, replay после reload, два реальных окна Chromium, конкуренцию обычной записи с outbox и смену владельца сессии. `snapshot().contacts` содержит поддержку lock, secure context, число pending событий, retryAttempt и последнюю ошибку.

Каталог охватывает доступные API задачи. Первый экран читает до 16 приоритетных задач, затем фоновые волны до 50 проверяют остальные. Историческое время задачи с выключенным сейчас учётом сохраняется. Подсказка обновления показывает число проверенных задач; неполный ответ или отказ доступа не объявляется полным результатом.

Для задач с записями срок свежести — 10 секунд, для ранее пустых — 120 секунд. Событие задачи и ручное обновление обходят ожидание. Это интервалы проверки открытой панели, к ним добавляются очередь и ответ сервера. Успешное сохранение обновляет сумму сразу; старый параллельный ответ не может её откатить. Закрытие панели отменяет ещё не отправленные волны.

Новый `CHANGED_DATE` из delta также обновляет конкретную задачу, включая ранее пустую; повтор той же даты не повторяет чтение. До окончания начального каталога его неполнота показывается отдельно.

Свежесть отсчитывается от фактического dispatch, исключая ожидание собственной очереди. Для нескольких страниц берётся самая ранняя отправка. Это отдельно проверяется при 15 секундах очереди и 9 секундах ответа: очередь не старит ещё не отправленное чтение, а задержка ответа учитывается.

Таймер хранит реальные секунды и подтверждённые ID каждого дневного сегмента. После потери ответа `add` нельзя автоматически определить, успел ли сервер создать запись: повтор требует проверки журнала и явного подтверждения пользователя. Такой intent переживает reload, редактирование и сброс ручной формы. Start/stop/cancel читают актуальный tracker под общей межоконной блокировкой. Отказ `server.time` сохраняет остановленную длительность до разрешения календарного дня и не записывает время с угаданной датой.

Перенос даты существующей записи остаётся за серверной обработкой `CREATED_DATE` с последующим перечитыванием. Это поле не описано в текущем перечне ARFIELDS метода update; принятие смены даты живым сервером не проверено. Подтверждённые сервером записи остаются источником итоговых сумм.

`read-state-regression.mjs` проверяет чтение всей переписки без ограничения видимым сообщением, реальные клики меню, независимое снятие reminder, двойной клик, порядок противоположных команд, ошибки и смену пользователя. Частичный успех чтения с ошибкой снятия reminder проверяется отдельно.

`native-desktop-batch.mjs` проверяет встроенный `BX.rest.callBatch`, доступный без SDK приложений BX24: 50 чтений — один транспортный запрос. Проверяются структурированные ошибки Desktop, сохранение 49 успешных ответов при одном отказе, отсутствие пропущенных страниц и запрет повторной отправки после лимита. Опциональный `PENA_NATIVE_REST_CLIENT` позволяет локально прогнать те же контракты через исходный SDK Bitrix с подменённым XMLHttpRequest; в CI скачивание стороннего SDK не требуется.

`time-refresh-regression.mjs` проверяет полноту, свежесть каждой задачи, мгновенное подтверждение CRUD, ревизии параллельных чтений, объединение обновлений и отмену. `time-acceptance-regression.mjs` — независимый API-стенд с отдельной базой данных: 41 задача, историческое N, более 50 записей на задачу, чужой автор/дата, неполные ответы и повтор страницы. JSON-отчёты этих наборов находятся в `tests/artifacts/`.

Контракты API: [пагинация tasks.task.list](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-list.html), [лимиты Bitrix24](https://apidocs.bitrix24.com/limits.html).
