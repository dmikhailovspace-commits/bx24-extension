# Аудит чтения сообщений и учёта времени 7.5.95

База сравнения — неизменяемый тег `v7.5.93`, commit `1de9595e50381b0f4ad94bb5fc7fc33d99ae04f2`. Проверки выполняются на действующих функциях runtime, отдельной модели API и настоящем Chromium. Там, где использован исходный SDK Bitrix, XMLHttpRequest подменён локальным серверным ответом: сетевых действий на пользовательском портале нет.

## Подтверждённые причины

| Проблема | До исправления | После исправления / проверка |
|---|---|---|
| «Прочитано» снимало reminder | Все 80 сообщений в серверной модели оставались непрочитанными | `im.dialog.read` без `MESSAGE_ID`, затем отдельное снятие reminder; все 80 прочитаны |
| Снятие «Прочитать позже» | Отдельного действия не было | Снятие сохраняет реальные unread-счётчики и упоминания |
| SDK `next()` вызывался как getter | 5 явных страниц → 15 HTTP-запросов, из них 10 неявных | 5 страниц → 5 запросов; все 250 задач сохранены |
| Встроенный batch Desktop игнорировался | 50 чтений → 50 одиночных запросов при отсутствии BX24 SDK | Встроенный `BX.rest.callBatch`: один запрос, те же 50 результатов |
| Неполный рабочий набор времени | В примере 41 доступной задачи читались 16, итог 0 вместо 1800 секунд | Проверяются все известные доступные задачи, историческое время задачи с N сохраняется |
| Устаревший кеш | Внешняя запись оставалась незаметной семь 15-секундных проверок, обновлялась через 120 секунд | Свежесть задач с записями — 10 секунд; ранее пустых — 120 секунд, событие и ручное обновление обходят TTL |
| Гонка чтения и сохранения | Старое чтение могло заменить подтверждённые 6000 секунд на 5400 | Ревизии диапазона/задачи защищают подтверждённое изменение; повторное чтение адресное |
| Двойной клик при проверке eligibility | Блокировка ставилась после ожидания API | Блокировка ставится до первого await; одна запись |
| Сервер повторял полную страницу | До 100 одинаковых запросов | Остановка после второго запроса с ошибкой, без ложного полного результата |
| Контакты при A→B→A и параллельном сообщении | Квалифицированное событие заменялось новой сессией | Неизменяемые события отдельно от текущей сессии |
| Старый дневной снимок другого окна | Стирал уже сохранённый и подтверждённый контакт | Все дневные изменения проходят общий Web Lock и читают свежий журнал |
| Сообщение после переключения задач | Контакт новой задачи мог получить название открытой старой карточки | Контекст сообщения ограничен его диалогом, каноническое название определяется по ID задачи |
| Предел локальной истории | 65 задач превращались в 40 | Все 65 сохраняются; обработка ограничена размером порции, а не обрезанием данных |
| Полночь и отложенная запись | Контакт мог попасть на день повторной попытки | Исходный timestamp и часовой пояс портала определяют дату; unresolved-событие ждёт корректного времени |
| Округление и границы суток таймера | Короткий таймер сохранял минимум минуту, длинный обрезался; переход суток не делился | Фактические секунды, отдельные дни, сохранение ID каждого сегмента; 20 секунд через полночь → 10 + 10 |
| Потерянный ответ add | Повтор мог создать дубль | Persistent intent и явная проверка журнала; редактирование формы не стирает неизвестный результат |
| Кеш таймера внутри блокировки | Второе окно могло читать старое состояние 500 мс | Start/stop/cancel читают authoritative storage внутри одного lock |
| Возраст кеша во время cooldown | Только что отправленный ответ считался старым из-за предыдущих 15 секунд очереди | Используется фактический dispatch каждой задачи, без лишнего повторного чтения после очереди |

Трёхкратное сокращение запросов на пяти страницах и сокращение 50→1 для batch относятся к указанным операциям. Это не доказательство такого же ускорения всего Bitrix или устранения пятисекундной задержки на живом сервере. SDK-ошибка создавала неконтролируемые повторные запросы и является подтверждённым источником лишней нагрузки.

## Точность и границы

Контакт — 60 секунд видимого просмотра задачи либо подтверждённое исходящее сообщение текущего пользователя. Быстрый просмотр, скрытая вкладка, входящее сообщение и обычный чат не квалифицируются. Перед сохранением проверяется актуальное `ALLOW_TIME_TRACKING`. События одной задачи в пределах 15 секунд объединяются в порядке их исходного времени; повтор доставки не добавляет контакт. Сам контакт не создаёт минуты.

Данные времени показываются постепенно: первая волна до 16 задач, следующие до 50. Закрытие окна прекращает ещё не отправленную работу. Неполный ответ, запрет доступа и ошибка API не объявляются полным результатом. Исторические подтверждённые записи сохраняются; новые записи требуют разрешённого учёта.

Контактный outbox требует HTTPS и Web Locks. При временной ошибке storage/сети событие сохраняется для повторной попытки; потеря процесса до первой успешной записи в storage не может иметь гарантии сохранности. Физический Mac и живой Bitrix в этих испытаниях не проверялись.

Bitrix add не предоставляет серверный ключ идемпотентности: после потери ответа состояние остаётся неопределённым до проверки журнала. Таймер сохраняет остановленную длительность при неизвестном часовом поясе. У update официально описаны длительность, комментарий и автор, но не CREATED_DATE; поле переноса даты оставлено с последующим чтением серверного результата, его поддержка живым сервером не доказана.

## Автоматические проверки

- `read-state-regression.mjs`: реальные клики меню, полный read, reminder, последовательность действий, partial success, ошибки и смена пользователя.
- `native-desktop-batch.mjs`: встроенный SDK, безопасное чтение cursor, структурированные ошибки, частичный batch и индексы ошибок нескольких пакетов. Опционально выполняет те же проверки через настоящий SDK.
- `time-refresh-regression.mjs`: полнота, свежесть, CRUD, ревизии, отмена и запись таймера.
- `time-acceptance-regression.mjs`: независимая серверная база, чужие записи, историческое N, пагинация и ошибочные ответы.
- `time-contact-journal-regression.mjs`: конкуренция, перезапуск, storage, дата, lease и два окна Chromium.
- Существующие функциональные, визуальные и нагрузочные наборы остаются частью полного `pnpm test`.
- Тест отправки разделяет синхронный стек DOM/Pull и отложенную очередь контактов: синхронных записей должно быть ноль, фоновых — не более одной. Отрицательные контроли намеренно нарушают каждую границу и проверяют обнаружение ошибки.

Артефакты в `tests/artifacts/`: `native-sdk-five-page-review.json`, `native-desktop-batch-official-sdk-report.json`, `read-state-baseline-v7.5.93.json`, `time-acceptance-baseline-v7.5.93.json`, `time-contact-before.json`, актуальные отчёты соответствующих наборов и `regression-summary.json`. Сводка полного прогона содержит SHA-256 каждого runtime-файла, длительности и ошибки; результат привязан к проверенному исходнику.
