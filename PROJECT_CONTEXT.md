## Назначение

Расширение запускается внутри Chromium-оболочки настольного Bitrix24 и дополняет нативный список чатов папками, поиском, фильтрами, сортировкой, мультивыбором и цветовыми маркерами. Основной принцип — не подменять верстку Bitrix24 собственным каталогом без необходимости.

## Изменения 8.0.10: действия на результатах поиска

- Полный CI выявил превышение бюджета отрисовки при совместном старте. Публикация большого индекса задач теперь идёт порциями по 100 с передачей управления между ними и проверкой прежнего аккаунта/владельца; cursor фиксируется только после окончания. UI получает одно итоговое обновление. При открытии панели метаданные видимого списка читаются до изменения DOM панели, чтобы не вызывать синхронный пересчёт её новой геометрии. Первая страница журнала содержит 20 записей; «Показать ещё» добавляет по 50 без REST и сохраняет открытый редактор. Итог считает весь журнал. Native-shared-task-startup проверяет обработку ввода между порциями и остановку при смене владельца/аккаунта. Два дорогих теста производительности перенесены в начало полного прогона без изменения порогов или состава 85 наборов.
- Воспроизведено отсутствие контекстного меню при ответе поиска через 650 мс: проход после ввода уже завершился, а новые SearchItem ещё не имели связи с native dialogId. Правый/Ctrl-клик теперь разрешает ID по живым props до обработки действия, не ожидая отрисовки. Это общий путь для чатов, задач, сотрудников и пользователей коллаб; числовой REST ID пользователя сохраняется.
- Отрисовка и мультивыбор учитывают поисковые карточки. Цветовые ореолы, видимое выделение и перенос используют существующие обработчики; Shift выбирает только видимый диапазон поиска. Поздние результаты получают unread-фильтр. Поисковые строки исключены из сортировки основной ленты и не считаются доказательством загрузки каталога.
- native-search-state расширен реальными кликами по поздней выдаче, обычному пользователю и пользователю коллабы без прежнего диалога: контекстное меню, Ctrl/Shift, массовые read/reminder, создание папки, цвет и ореолы. Проверка изоляции аккаунтов и сохранения запроса сохранена. Нативные API заменены контролируемыми ответами в тесте, живой авторизованный портал не проверялся.
- Последующее указание пользователя возвращает полный прогон и публикацию GitHub. После локального аудита основных подсистем CI проверяет все 85 наборов на точном релизном коммите. Только после успешного gate собираются Windows EXE и macOS Universal DMG. В verify-source дополнительно собираются и проверяются Chrome ZIP и материалы Store; публикация прикладывает их к релизу, отдельно от четырёх desktop-файлов в dist. ## Изменения 8.0.9: поиск и фильтр непрочитанных

- Поиск сохраняет запрос при открытии результата и клике вне списка. Привязка к смонтированному RecentListContainer/TaskListContainer сохраняет нативные поиск, выдачу и открытие диалогов; крестик и Escape явно очищают запрос. Повторное создание поля восстанавливает запрос. Хранение разделено по origin, числовому пользователю и режиму, смена аккаунта очищает чужой запрос.
- Производственный фильтр использует отдельный CSS-класс, не запоминает и не перезаписывает inline display Bitrix. Отложенное завершение поиска больше не оставляет строки навсегда скрытыми. При поиске папка не ограничивает штатную выдачу, а «Только непрочитанные» применяется к ней.
- Настоящие SearchItem не имеют data-id и badge: ID читается из props живого Vue-компонента, отсутствие значка не обнуляет счётчик. Используются модель Messenger и сохранённые метаданные. Обход Vue ограничен активным списком, ссылки кешируются с проверкой аккаунта и размонтирования.
- Запрос папки группирует алиасы одного участника; любой найденный нативный ID завершает его ожидание. Общий unread-фильтр также может догрузить известные непрочитанные записи через штатный сервис. Состав папок сохраняется при пагинации, ошибках и достижении конца списка; отсутствие в DOM не удаляет запись.
- Сверены публичные recent-container.bundle.js и search/registry.bundle.js портала bx24.id-pr.ru. Адресное воспроизведение использует настоящий production Vue 3.5.28 и контракт нативных обработчиков. Сброс поиска воспроизведён на сохранённом runtime 8.0.8. Проверяются оба режима, выбор результата, поздний ответ, отложенная очистка, remount, смена аккаунта и unread-выдача без DOM-счётчика. Живой авторизованный клиент и фактический состав папок пользователя не проверены.
- Поставка локальная: Windows EXE. Полный пакет, GitHub и macOS не запускаются по текущему указанию пользователя.
- Приёмка 8.0.9: 6/6 адресных наборов за 83,1 секунды; отдельно проверены готовый EXE и контекст. Установщик собран из замороженной копии 19 runtime-файлов с хешами прогона. ## Изменения 8.0.8: штатная пагинация Bitrix для папок

Папки фильтруют исходные строки Bitrix, а отсутствующие участники подгружаются фоновыми страницами через getRecentService().loadNextPage() уже смонтированного RecentList/TaskList. Расширение не создаёт собственный сервис, не сбрасывает курсор и не меняет его размер страницы. Подробности диалогов для папки больше не запрашиваются параллельно отдельным REST-проходом.

- Смена папки/поиск/скрытие/смена режима или аккаунта прекращают дальнейший обход. Уже отправленный штатный запрос не отменяется: новая работа ждёт его, не создавая дубль. ## Изменения 8.0.6: нативная загрузка по мере прокрутки

- Полный обход истории больше не запускается при старте, поиске, открытии папки, обновлении или возврате в приложение. Общий список и прокрутка принадлежат Bitrix; расширение сохраняет метаданные появляющихся строк без удаления отсутствующих. Блокирующая «Прогрузка диалогов» отключена. Старый движок полного каталога сохранён только для явно включённых диагностических режимов.
- Ввод, фокус и клавиатура штатного поиска больше не перехватываются. Bitrix отвечает за удалённый поиск, сотрудников без переписки и пагинацию результатов. Поиск не ограничивается папкой или сохранёнными названиями, его результаты не импортируются как полный каталог. Отдельная секция сотрудников PENA в этом режиме отключена.
- Внутри выбранной папки/группы используется существующее виртуальное представление сохранённых участников: оно позволяет открыть старый диалог, которого пока нет в нативном окне. Загружаются только детали участников выбранной папки, с прежними ограничениями параллельности/повторов и защитой от ответа другого аккаунта. Возврат к общему списку восстанавливает нативный DOM и позицию. Скрытая исходная строка и проекция папки не являются источниками нулевого счётчика; приоритет имеет модель Messenger и сохранённые метаданные.
- Сортировка «Сначала старые» удалена для даты; сохранённое значение asc мигрирует в desc. Общая лента сохраняет порядок Bitrix, включая закрепления. Цветовые маркеры и мультивыбор сохраняются. Возврат в Messenger независимо запускает дедуплицированное обновление панели «Сегодня»; оно не требует обхода диалогов. Проверка snapshot покрывает оба режима и удержанный прежний guard.
- Новый native-lazy-list-regression проверяет рабочий режим без принудительных флагов загрузки в чатах и задачах: малое начальное окно, отсутствие обхода/REST recent/загрузочного экрана, старую карточку в папке, счётчик, Ctrl-клик и удалённую выдачу поиска. Старые тесты полной материализации явно включают диагностический legacy-режим; они не считаются доказательством нового поведения. Производственные startup-time и startup-cycle без тестовых флагов проверяют начальное окно без обхода, полный журнал времени, отложенную авторизацию и позднее подключение хранилища без прокрутки к хвосту. Проверка живого авторизованного клиента не выполнялась.

Быстрому локальному восстановлению дано 100 ms; затем список начинает загрузку, а поздний снимок объединяется с актуальными данными. Его подтверждённые физические ID остаются нижней границей: пропущенный ID требует восстановления текущего поколения. Фоновая запись кеша не удерживает готовность загрузки.
- При неизвестном типе `im.recent.list` нативный аудит присоединяется к уже работающему полному каталогу задач этой identity. Сам он не запускает обход задач. Неполный/head-only результат не разрешает ускоренное подтверждение списка. На одинаковом Chromium-сценарии с 108 диалогами: полный проход 7929 → 2697 ms (2.94×), прежние 2 страницы задач + 1 страница диалогов, те же ID, хвост и позиция прокрутки. Это стендовый результат конкретного сценария, не измерение живого Bitrix.
- Профиль `time-focused` расширен до 20 suites; реестр — 75. Новые браузерные сценарии запускаются без открытия панели, прямого вызова bootstrap и специальных runtime-флагов. Проверяются поздняя identity, недоступный/поздний repository, ошибка даты и общий каталог задач. Полный реестр в этой итерации не запускается.

## Изменения 7.5.123: чтение времени без постоянной полосы

- Полоса загрузки/ошибки трудозатрат удалена из DOM и CSS панели. Начальная загрузка, включая ожидание каталога после сохранения проектов, и неизвестный итог обозначаются короткой строкой в существующей сводке. Неизвестный итог не выдаётся за отсутствие записей; неполный итог начинается с «Часть данных». Ошибка фонового чтения сохраняет подтверждённые значения и доступна в подсказках сводки/кнопки. Ручная проверка обозначается `aria-busy` на кнопке и сообщает ошибку отдельным уведомлением. Ошибки ADD/UPDATE/DELETE и неопределённого результата записи не скрываются.
- Числовые ошибки Bitrix и `ERROR_CORE` при первом запросе общего журнала больше не считаются безусловным отказом всего чтения. Один запрос конкретной разрешённой задачи проверяет доступность обычного метода. Только корректный ответ разрешает запасной проход; проба не подтверждает сумму или пустой день. Квота, таймаут, поздняя ошибка страницы, неверная проба и смена scope не запускают массовые запросы.

Сценарий 100 задач / 99 подтверждённо пустых требует 3 запроса, включая проверку совместимости; повторное открытие — 0. Это стендовый бюджет, не измерение живого портала.
- Диагностика чтения содержит исходный код ошибки, число попыток глобального чтения, длительность и финальное состояние. Браузерные проверки ожидают фактическую полноту снимка, а не наличие полосы.

## Изменения 7.5.120: журнал времени и сохранение состояния

- Холодное чтение трудозатрат и ручная проверка сначала запрашивают общий журнал текущего пользователя за выбранные даты через `task.elapseditem.getlist` с taskId 0. Это возможность серверной реализации, поэтому ответ проверяется: пользователь, дата, положительные ID, порядок, размер и полнота страниц. Пустой ответ требует подтверждения доступности общего журнала; неподдерживаемый метод переключает эту identity на прежний ограниченный обход. Таймаут, квота или ошибка доступа не запускают массовый запасной обход. Контролируемый сценарий 4149 задач / 321 запись требует 7 страниц журнала; это измерение числа запросов, не гарантия скорости живого портала.
- После полной загрузки повторное открытие использует кеш; изменённая задача читается точечно. Собственный подтверждённый ADD, включая остановку таймера, сохраняет свежесть записи. Глобальное чтение ждёт полного выбранного каталога и подтверждённой даты портала; результаты принимаются только для актуальных scope/revisions. Диагностика `__PENA_TIME_LOAD_DIAGNOSTICS__.snapshot().read` содержит стратегию, число задач/страниц и причину запасного обхода.
- Сохранение проектов переносит подтверждённый снимок в новый scope без очистки контактов и таймера. Расширение выбора показывает прежнюю сумму до ответа; сужение не выдаёт старую сумму за подтверждённую. Права чтения, свежесть и маркер глобального прохода не переносятся. Сегодня и выбранный диапазон защищены от вытеснения из кеша на восемь записей. Поле `TIME_SPENT_IN_LOGS:null` никогда не стирает известные записи без чтения журнала.
- Подтверждённый контакт с задачей разрешает выбрать её для внесения времени в этот день даже вне выбранных проектов. Перед записью заново проверяются доступ и `ALLOW_TIME_TRACKING=Y`. Подтверждённые квитанции сохраняют внесённое время при повторном чтении и переходе суток, но сами не разрешают новый таймер. Контакты сортируются по убыванию контактов после последнего внесения; при равенстве — по последнему взаимодействию. Поиск строит разрешённый набор один раз, без перечитывания журнала для каждой задачи.
- Ручное «Добавить» занимает busy до ожидания межоконной блокировки и ждёт её освобождения; фоновое восстановление остаётся неблокирующим. Повторное нажатие не создаёт очередь дублей. После ожидания сверяются пользователь, портал и выбор проектов. Busy сохраняется до завершения восстановления подтверждённой записи и освобождения блокировки. Граница учтённых контактов фиксируется при нажатии, поэтому взаимодействия во время ожидания остаются для следующего внесения. Регрессия проверяет удержанную WebLock, двойное нажатие, смену scope и задержанное сохранение контактов.
- Если контакт или обновление задачи меняет ревизию во время проверки допуска к учёту времени, один общий владелец запроса повторяет устаревший GET не более одного раза. Все ожидающие действия используют этот результат; двадцать ожидающих не создают двадцать повторов. Ошибки сети, неизвестный флаг, смена пользователя/проектов и отмена не запускают такой повтор. Свежий `ALLOW_TIME_TRACKING=N` запрещает запись. Завершение старой проверки не удаляет более нового владельца из очереди.
- Отложенный автофокус часов после выбора контакта применяется только при неизменном фокусе, выбранной задаче и открытой подключённой панели. Выбор минут или другого элемента пользователем отменяет автофокус. Это предотвращает перенос ввода минут в часы при задержанной отрисовке. Браузерная проверка удерживает callback, вводит минуты, освобождает его и продолжает ввод; обычный автофокус и отмена после закрытия/замены панели проверяются отдельно.
- Новые предметные проверки: `time-global-elapsed-regression`, `time-counter-reset-regression`, `time-contact-project-exception-regression`. Последняя включает Chromium-флоу добавления задачи вне проекта, повторного чтения, reload и сохранения всех проектов при задержанном ответе. Стартовые стенды поддерживают числовые ID журнала, глобальный фильтр пользователя/даты, ID keyset и отдельную неподдерживаемую ветку; сетевые бюджеты различают общий журнал и точечные запросы. Полный `pnpm test` выполняется на замороженном релизном commit в CI; локально во время правок запускаются затронутые сценарии. CI использует `PENA_TEST_FAIL_FAST=1`: первая ошибка останавливает непригодный к выпуску прогон. Обычный локальный `pnpm test` продолжает собирать все ошибки. Живой портал и физический Mac не заменяются стендами.

## Архитектура

### Браузерная поставка Chrome 7.5.131

- `extension/` и четыре desktop-артефакта 7.5.129 остаются источником и поставкой настольного Bitrix. `chrome/` содержит только браузерные адаптеры, нейтральное оформление и popup. Публичное имя — «Сортировщик чатов Bitrix24»; это самостоятельная разработка без бренда PENA в карточке магазина.
- `node tools/build-chrome.mjs` создаёт `chrome-release/unpacked/`, `BX24_Chat_Sorter_Chrome_v7.5.129.zip`, SHA-256, полный `build-manifest.json` и `publishing/`. ZIP содержит manifest в корне и только явный runtime-набор. Сборка детерминирована, desktop `dist/` не затрагивается; исходные 19 файлов и итоговый Chrome payload перечислены с хешами. Ключ desktop ID удаляется: ID публикации назначает Chrome Web Store. Для обновлений unpacked нужно сохранять путь папки.
- Chrome 106+, HTTPS-порталы. Нет обязательного доступа ко всем сайтам. `activeTab` нужен для адреса выбранной пользователем вкладки, `scripting` — для подключения, `storage` и `unlimitedStorage` — для локального каталога и надёжной очереди. Optional HTTPS permission запрашивается кнопкой для одного scheme+hostname; Chrome не разделяет права по портам. Авторитет — `chrome.permissions.getAll`, persistent registrations пересогласуются при старте и выдаче/отзыве доступа. Открытые вкладки после отключения требуют перезагрузки, ранее внедрённый JS Chrome автоматически не выгружает.
- Chrome worker дополняет прежний versioned entry, сохраняя health/build/protocol. Только собственный content script с разрешённого HTTPS-хоста и допустимой поверхности может запросить внедрение фиксированного списка модулей. Все операции привязаны к sender.documentId, проверяется отзыв разрешения; данные сообщения не могут задать код, файлы или целевую вкладку. JS внедряется через MAIN world, CSS через scripting. Per-document claim предотвращает двойной запуск после перезапуска worker; частичная загрузка требует reload. Успешность подтверждается API модулей и версией runtime.
- Build transforms имеют строгие anchors, при дрейфе исходника сборка падает. Browser loader сохраняет bridge и проверку manifest, но не вставляет script/link в DOM. Адреса локальных шрифтов преобразованы через `__MSG_@@extension_id__`, чтобы insertCSS не искал их на портале. Web-accessible только manifest, значки и шрифты. Внешний отчёт конкретного агентского портала и desktop GitHub updater исключены; Store обновляет версию сам. Исходные desktop-файлы не переписываются.
- Четыре Chrome suites проверяют ZIP/manifest/идентичность общих файлов, разрешения и гонки worker, реальный DOM popup, установленный MV3 в Chromium (отсутствие начальных grants, granted-host fixture, nonce-only script CSP, реальные шрифты, чужие сайты, reload worker/profile). Диалог разрешения Chrome и живой авторизованный Bitrix остаются ручной приёмкой; fixture-grant в тестовом manifest не выдаётся за пользовательский consent. Произвольные Messenger iframe и порталы с обязательными Trusted Types без совместимой политики не объявляются поддержанными.
- Материалы магазина в `docs/chrome/`: описание, privacy, установка и reviewer notes. Публичная политика, действующий контакт издателя и закрытая тестовая учётная запись предоставляются владельцем публикации. Подготовка ZIP не означает отправку или одобрение Chrome Web Store. Перед выдачей выполнить полный `pnpm test`, сборку Chrome и context `-Check`.

- `extension/content.js` проверяет цельность установленного релиза и последовательно внедряет runtime-модули только в поддерживаемую поверхность: top-level Messenger/desktop launch либо служебный `/desktop_app/?IM_LINES=Y` frame. Произвольные task/side-panel iframe не получают CSS и runtime. Health-check worker запускается неблокирующе: недоступный worker не задерживает отрисовку интерфейса, а repository-клиент восстанавливает соединение своей dirty/retry-очередью.
- `extension/injected.js` управляет интерфейсом, загрузкой диалогов, сортировкой, папками, поиском и интеграцией с нативным DOM Bitrix24.
- `extension/native-*.js` содержат изолированные модели каталога, состояния взаимодействия, времени и жизненного цикла.
- `extension/dialog-repository.js` — клиентский мост к хранилищу.
- `extension/worker-v7_5_131.js` — release-specific MV3 entry с явными build/protocol-маркерами; новое имя worker обязательно при каждом patch-релизе, потому что Chromium-оболочка Bitrix24 может сохранить регистрацию и ScriptCache старого unpacked worker после замены файлов.
- `extension/background.js` — импортируемое ядро service worker с каталогом диалогов в `chrome.storage.local`.
- Windows-updater всегда собирает пустой staging строго по `update.extension_files`, сверяет полный набор файлов и оба встроенных шрифта, а имя worker берёт из `manifest.background.service_worker`. Старые generic/versioned worker и любой лишний runtime не переносятся в новую установку; до атомарной замены сохраняется рабочий rollback.
- `.github/workflows/build-macos.yml` — единственный удалённый путь выпуска macOS DMG: сборка и проверка выполняются на GitHub-hosted `macos-15`.
- Область каталога: `portalHost~userId`. Запрос страницы принимается только при совпадении `portalHost` с origin.
- Репозиторий использует schema v2: `revision`/`baseRevision`, идемпотентный `operationId`, persistent lease fence и CAS-цикл `get → merge → retry`. Подтверждённый полный снимок удаляет только записи, которые существовали в его базовой ревизии и получили явный tombstone; новая запись другой вкладки при конфликте сохраняется. Ошибка worker/storage не отключает репозиторий: dirty-очередь ждёт reconnect и повторяет запись. Событие фактического подключения bridge немедленно будит bootstrap и обходит накопленный backoff. Поздний reconnect не делает blind restore: remote snapshot объединяется с живыми dirty-записями по base revision и свежести, поэтому собранные без worker ID не теряются, а старые tombstone не возвращаются.

## Продуктовые контракты

**Приоритет с 8.0.6:** действуют правила нативной ленивой загрузки, штатного поиска и папок из раздела 8.0.6 выше. Упоминания полной материализации, tail-proof и изоляции поиска ниже описывают сохранённый диагностический движок, а не запуск обычного клиента. Общий список не обходит историю автоматически.

- Нативная лента и нативный scrollbar Bitrix24 должны сохраняться. Нельзя допускать скачков прокрутки или принудительного смещения экрана.
- Нативный режим — единственный рабочий режим. Значение `pena.dialogControlNative.v1.*=0`, оставшееся от удалённого каталога, автоматически мигрирует в `1`; старый флаг не может скрыть папки, сортировку или панель времени на обновлённом профиле.
- По умолчанию сортировка — по дате, новые сверху, но свежий нативный порядок Bitrix24 не перестраивается расширением без явного пользовательского действия. Для уже показанной нативной строки приоритет имеет дата/время, которое показывает сам Bitrix24; две реальные даты сравниваются хронологически, а синтетический `native-order` никогда не сравнивается с timestamp как календарное время и остаётся стабильным рангом. Строки без даты уходят в конец в обоих направлениях. Когда полный набор действительно нужен поиску, папке, unread-фильтру, пользовательской сортировке, ручному обновлению или recovery, каталог загружается динамически до фактического конца без лимитов 100 или 500 диалогов.
- Состояние каждого режима разделено на `catalog`, `materialization` и `attempt`. Метаданные репозитория не могут объявить нативный DOM готовым, а ошибка отдельной попытки не портит последний подтверждённый каталог. Публичный статус пригодного каталога остаётся `ready`; ошибка его фонового обновления публикуется только как `backgroundError` и не создаёт красный retry. Ошибка, прогресс и recovery-action привязаны к своему режиму: при chats↔tasks они не могут мигнуть в чужом toolbar даже на один кадр. DOM-free boundary snapshot публикует новый режим прямо в MutationObserver, а тяжёлый lifecycle-reconcile остаётся покадрово дедуплицированным. Переиспользуемая панель перед сменой host скрывается как `mounting`, затем атомарно получает новые папки, счётчики и status chip.
- Один source-bound reconcile дедуплицирует события по mode/list/viewport/source-generation; отложенный запрос старой вкладки не может передать новой вкладке `tailProbe`, поставить ей recovery после debounce или записать ей результат. Выбран гибридный interaction-first контур: при первом запуске Bitrix24 видимый список «Чаты» автоматически проходит полную guarded-materialization с API-проверкой и восстановлением позиции; первый вход в «Чаты задач» делает то же для своего source. Повторное открытие готового source, `focus`, `resize` и короткий возврат видимости не запускают полный обход. Истечение TTL API-каталога само по себе не инвалидирует подтверждённый нативный DOM. Помимо первого открытия нового source, полная materialization запускается по потребности полного представления: поиск, папка, unread-фильтр, пользовательская сортировка, ручное обновление либо recovery схлопнувшегося/потерянного source. Физическая проверка хвоста выполняется после `resume/pageshow.persisted`, скачка таймера от двух минут, скрытия дольше 15 минут, подтверждённого offline→online или доказанной потери source; пачка событий создаёт один reconcile.
- DOM-материализация не имеет TTL. После долгой паузы reconcile проверяет source-generation, диапазон, head-сигнатуру и пять хвостовых ID. Хвост проверяется коротким bottom-probe под общим visual guard с восстановлением ID-якоря и пиксельного смещения. Успех требует 5/5 ID; каждый отсутствующий ID проверяется через API, и полный проход не нужен только если все пропуски подтверждены как недоступные. Любой всё ещё доступный хвостовой ID, смена source или схлопнувшийся диапазон запускают ровно один полный native-scroll под overlay.
- Полный проход не принимает `idle` или кратко неподвижный `scrollTop` как доказательство конца: viewport обязан физически достичь `maxTop`, source-generation не должна измениться, loader Bitrix должен исчезнуть, а итоговый набор не может быть меньше прошлого подтверждённого поколения. Обычный низ подтверждается четырьмя выборками; холодный source использует 24 выборки, пока нет точного fast-path proof, и шесть выборок после него. Временная неподвижность recycled viewport допускается до 2,6 секунды и сбрасывается при любом реальном прогрессе. До 20 пропавших ID проверяются с concurrency 2. Freeze/hidden приостанавливают проход и его active-time timeout; смена режима/source аннулирует старую попытку. Ошибка, offline, `stalled` или timeout сохраняют предыдущий каталог и получают до трёх автоматических retry 1/2/5 секунд без hard-error, toolbar-action и blocking overlay между попытками. После исчерпания бюджета остаётся одна стабильная ручная кнопка без фонового таймера. Retry скрытого или неактивного режима хранится как dormant-state и не перевзводит таймер; `mode-switch`, возврат видимости и `online` будят один дедуплицированный recovery.
- Процент нативной прогрузки измеряет весь foreground-процесс, а не только положение scroll thumb: первый/второй проход, стабильные выборки хвоста, head-fence, атомарный commit и восстановление пользовательского якоря. Пока попытка активна, значение ограничено 99%; 100% публикуется только после commit и возврата viewport. Прогресс монотонный и обновляется не чаще одного раза за 120 мс, чтобы пересчёт счётчиков и toolbar не тормозил основной поток Bitrix. Повторная ручная проверка уже подтверждённой ленты считается тёплым однопроходным сценарием и использует всю шкалу 0–99, а не холодный диапазон первого прохода 0–49.
- У холодного поколения параллельно строится дополнительное доказательство ожидаемого набора ID. Schema-v2 snapshot с явным `confirmedIds` служит нижней границей и быстрым bootstrap. `im.recent.list` считается метаданной проекцией, а не точной копией физической вкладки: API может вернуть служебные или относящиеся к другой нативной проекции ID. Поэтому точное совпадение API и DOM ускоряет холодный source до одного прохода, но API-only ID только записываются в `apiProjectionExtraCount` и не инвалидируют физически подтверждённую ленту. Блокирующим доказательством пропуска остаются ранее подтверждённые физические `confirmedIds` того же режима. Если точного API-proof нет, выполняется второй guarded-pass. Неполный/offline-аудит сохраняет готовую ленту и переходит в отдельный metadata-retry 1/2/5/15/30/60 секунд: он не меняет materialization, не показывает status chip/overlay и не запускает прокрутку. Даже два пустых ответа API не доказывают пустой каталог без видимого нативного empty-state Bitrix.
- Успешный холодный API-аудит сохраняется как общий снимок `Chats + Task Chats` на 24 часа. Task-часть фонового прохода ограничена четырьмя свежими страницами `tasks.task.list` и не удерживает Messenger; полный task-индекс строится только по явному ручному запросу или потребности полного task-view. При первом входе во второй режим снимок привязывается к его новой source-generation и повторно используется как ожидаемая нижняя граница. Физическая materialization всё равно доказывается отдельно для реально открытого нативного списка; общий REST-снимок никогда не объявляет скрытый DOM готовым.
- Полный API-аудит привязан к portal/user/mode, schema, source-generation и identity нативного source. Запоздалый результат после смены пользователя, режима или source отбрасывается. Его метаданные объединяются с live-состоянием по свежести сообщения, счётчиков, availability и task-классификации; старый аудит не может откатить более новое сообщение, дату, непрочитанное, `taskCatalogFetchedAt` или tombstone ни в общем каталоге, ни в снимке текущего прохода. Реально заменённый source всегда считается холодным поколением и получает новый recent-аудит, а не наследует доказательство предыдущего DOM. Новый live ID, пришедший в середине прохода, сохраняется metadata-only, но не добавляется в `seen`/`confirmedIds`, пока его физически не показал нативный source.
- Полный индекс task-чатов загружается через `tasks.task.list` страницами по 50 строк с ID-keyset: `ID asc`, `>ID`, `start=0`. Автоматическое обновление берёт только свежую голову, сортированную по `ACTIVITY_DATE`, и запускается после устойчивого пользовательского простоя; полная пагинация разрешена единому начальному циклу сегодняшних трудозатрат, ручному обновлению, task-поиску с недостаточным локальным индексом либо полному task-view. Обычное открытие чата и отправка сообщения не запускают REST, traversal, overlay или синхронную запись `localStorage`. Фоновая глубокая проверка отложена минимум на две минуты, требует 30 секунд отсутствия взаимодействия, проверяет активность после каждой страницы и прерывается, как только пользователь возвращается к Bitrix. Выбор папки или точный поиск проверяет только совпавшие pending-ID; пустой message-preview получает cooldown и не создаёт повторный detail-запрос на каждом render. Свежие title/avatar из `im.recent.list` имеют приоритет над запаздывающим `im.dialog.get`, поэтому detail-enrichment не откатывает нативную проекцию Bitrix. Индекс жёстко scoped по portal/user, отбрасывает ответ сменившегося scope и публикует названия/eligibility отдельно от dialog-каталога. Он связывает задачи с чатами по `CHAT_ID`; дата сортировки старой задачи берётся из последнего сообщения, иначе из `ACTIVITY_DATE`/`CHANGED_DATE`. API-индекс не считается доказательством полноты task-ленты.

- Запрещён кэшированный replacement/continuity-список: расширение не создаёт собственные строки вместо строк Bitrix и не определяет полноту по числу элементов виртуального DOM. Для режима сохраняются identity списка/viewport, source-generation, диапазон, подтверждённый полный набор ID, пять head/tail ID и доверенная пользовательская позиция. Эти данные нужны только для проверки и восстановления нативного источника, а не для подмены его отрисовки.
- `im.recent.list` остаётся источником метаданных для совместимости, тестов и фонового обновления головы, но не считается доказательством, что старые строки появились в оригинальной ленте. Его пагинация использует `LIMIT=200`: явный валидный `next` имеет приоритет, без него `OFFSET` растёт на запрошенный `LIMIT`, а не на число строк в схлопнувшейся странице. Пересечения дедуплицируются; нулевой или заниженный `total` служит только прогрессом и не обрывает проход. Полный `tasks.task.list` продолжает обход через `>ID` последней строки, проверяя строгую монотонность ID; короткая страница без признаков продолжения подтверждает хвост. Только ограниченная свежая голова по ACTIVITY_DATE использует явный `next` или `START += 50`.
- Таймаут лёгкой фоновой проверки головы не заменяет готовый атомарный каталог ошибкой и не запускает вслед за собой второй медленный `im.recent.list`; проверка тихо откладывается до следующего окна свежести. Жёсткая ошибка полной загрузки всегда имеет приоритет над остаточным счётчиком. Если не подтверждён именно сохранённый папочный диалог, статус и подсказка показывают его название и ID, а не безымянное «Не загружено: 1».
- Синхронизация разделена по стоимости: голова `im.recent.list` — 1 минута, task-индекс — 15 минут, полный REST-аудит метаданных — 24 часа. API-курсор и время полного API-аудита хранятся отдельными versioned watermarks; время записи кэша, нативного прохода или visible-window merge ими не является. Старый manifest без явного API-watermark после обновления получает курсор `0` и проходит один полный аудит. Курсор полного аудита фиксируется в момент его старта, чтобы следующая дельта не пропустила события, пришедшие во время пагинации. Фоновые проверки работают только через API, никогда не прокручивают реальный viewport и не показывают loader. REST может добавлять и обновлять записи, но не объявляет DOM материализованным, не отменяет native-scroll и не удаляет записи по неполному ответу.
- Generic `im.dialog.get` может вернуть task-чат как обычный `chat` без `TASKS_*`-признаков. Такой detail разрешено использовать для аватара, текста и доступности, но он не может понизить уже подтверждённый `isTask`, стереть `taskId`/`taskUrl` или перенести диалог между режимами.
- Поиск, активная папка, сортировка, маркеры и per-mode scroll-anchor переживают probe/recovery без сброса. Восстановление не имеет права показывать диалог из другой папки, создавать replacement-строки, скрывать нативный scrollbar или оставлять viewport в служебной позиции.
- Additive/visible-window hydration не выполняет identity-remap и не удаляет элементы. В полном reconcile валидный ID сильнее временного title, канонический `dialogId` сильнее совпадения по названию; единственное специальное преобразование — доказанная legacy-коллизия `chatN → userN` с тем же числовым ID и уникальным именем личного диалога. Поэтому одинаковые или временно устаревшие заголовки не могут сократить каталог либо перекинуть папочный диалог в другой режим.
- Уменьшение `scrollHeight`, вызванное собственной фильтрацией PENA через `display:none`, относится только к presentation-слою и не инвалидирует уже подтверждённую materialization того же source-generation. Реальное схлопывание источника после долгой паузы проверяет tail-probe: он временно раскрывает нативные строки, сверяет физический диапазон и сохранённые хвостовые ID. Недостающие ID точного API-baseline инвалидируют старую same-node materialization даже при неизменном `scrollHeight`. Retry ограждён per-mode epoch и source-generation fence; старый timer может отменить восстановление как уже завершённое только после коммита более новой физической revision. Отложенный `initial-mount`/`source-ready` timer не должен запускать второй полный проход из-за активной папки, поиска или фильтра.
- После `ready` Bitrix может переиспользовать небольшой пул DOM-строк и показать более старые ID только при ручном движении вниз. Такое recycled-окно немедленно получает текущие папку, поиск, маркеры и сортировку, даже если параллельно идёт REST-аудит. Шаг полного прохода ограничен измеренной высотой нативного пула и всегда оставляет минимум четыре строки перекрытия; если `scrollHeight` вырос во время подтверждения старого низа, следующий шаг выполняется только один раз с обязательными scroll-event и capture. Ранг новых нижних ID продолжается после максимального подтверждённого `nativeRecentRank`, а не начинается локально с нуля; head/tail-якоря также сортируются по этому стабильному нативному рангу, а не по случайному порядку повторного обнаружения. Exact fast-path подтверждает низ шестью выборками примерно за секунду и выполняет guarded head-fence; неопределённый холодный проход сохраняет 24 выборки примерно за 3,8 секунды и второй проход. Любая поздняя строка, новый head ID или изменение диапазона сбрасывает короткое подтверждение, включается в materialization и не меняет пользовательский scroll-anchor.
- Фоновый REST-аудит и detail-обогащение могут заменить синтетическую дату реальной датой сообщения, но не имеют права стирать доказанные `nativeRecentRank` и `lastMessageTsSource`. Оба поля проходят через metadata, managed merge и hydration нативных строк. Иначе поздняя строка сначала попадает в текущую сортировку, а после атомарного REST-коммита перемещается в неверную часть ленты. Regression-сценарий трижды переназначает ID одного пула и проверяет оба направления сортировки до, во время и после медленного REST-аудита при неизменном scroll-anchor.
- Верхние счётчики вкладок, групп и папок показывают сумму непрочитанных уведомлений, а не количество вложенных диалогов. Изменение нативного counter/status обновляет каталог и все связанные badges тихо, без loader, прокрутки и повторной materialization; обработчик fenced по mode/source-generation. Скрытые счётчики и mention-маркеры не считаются активными. Частичный успешный `im.counters.get` обновляет только явно присутствующие namespace и ID: отсутствующие поля нельзя обнулять, пока полнота ответа не доказана.
- MutationObserver нативной ленты разделяет изменения identity, счётчиков и содержимого строки. Предпросмотр сообщения, delivery-state и typing не запускают полный visible-window merge, сортировку каталога, общий repository commit или REST; активный поиск обновляет только затронутую строку, а счётчики агрегируются через один индекс каталога вместо повторного сканирования DOM. Пересозданный Bitrix-индикатор над цветной аватаркой получает короткий row-local repair слоя без перестройки ленты. Реальные новые/recycled строки никогда не подавляются общим 180-мс флагом собственных перестановок: они сразу получают текущие маркер, фильтр и сортировку, при этом metadata-only API-проекция остаётся в каталоге и не смешивается с точным количеством физически материализованных строк.
- Loader один для всех режимов: `Прогрузка диалогов`, линия и числовой процент без поясняющего текста. До первого распознанного окна показывается честное `0%`; затем процент меняется только по измеренному физическому диапазону и числу найденных ID, без искусственного floor `6%`. Неподвижный не-нижний viewport после bounded stall переходит в retry, а не висит до общего таймаута. Loader перекрывает всю панель, следует за её размером и используется только при первой материализации режима в текущем документе, ручном полном обновлении или восстановлении неполного/несовместимого состояния. Фокус, разворачивание окна, resize, фоновая дельта и тихое обновление просроченного снимка не показывают loader. Пока холодный нативный проход не завершён, массовая проверка отдельных папочных диалогов не запускается. Фоновый task-индекс не блокирует интерфейс. Компактный статус после успеха скрыт. `retry-wait` означает будущую попытку, а не активную работу: публичный `inFlight=false`, foreground overlay снят. Локальный `aria-busy` или loader внутри строки не считается загрузкой всей ленты; учитываются только list-level признаки в пределах viewport. Автоматический retry поверх текущей `ready`-materialization остаётся только диагностикой и не показывает ложное «Повторить»; пользовательская кнопка появляется лишь когда repair действительно обязателен, и запускает один дедуплицированный recovery.
- При включённом расширении поле поиска визуально остаётся нативным, но события перехватывает отдельный поток PENA: он фильтрует известные диалоги и в режиме чатов дополнительно ищет сотрудников портала через `im.search.user.list`. Секция сотрудников не входит в каталог диалогов и не ограничивается выбранной папкой. Запрос хранится независимо, не сбрасывается при открытии диалога или клике вне строки, а очистка возвращает полный список и убирает карточки сотрудников. Автофокус Bitrix при запуске снимается; реальный клик пользователя по строке поиска сохраняет фокус. Фильтрация не удаляет нативную верстку и цветовой маркер строки.
- Папки не заменяют нативные строки. Диалоги внутри папки обязаны оставаться доступными фильтрации и сортировке.
- Пользовательскую папку можно drag-and-drop перенести с вкладки «Все» или из другой группы на вкладку целевой группы; вложенные диалоги перемещаются вместе с ней. Системную вкладку «Все папки» можно переставлять внутри строки папок, но она остаётся синтетическим агрегатом: не сохраняется как папка и не привязывается к группе. Нативный HTML5 drag диалога переживает штатный Chromium `pointercancel`: payload живёт до `drop`/`dragend`, поэтому перенос на «Все папки» всегда снимает папку и цветовой маркер.
- Цвет назначается вручную только диалогу, состоящему в папке. Цвет папки не наследуется диалогами при переносе, отображении, выборе цвета или сортировке. Собственный цвет сохраняется при переносе между папками. При удалении из папки цвет и контроль маркера удаляются.
- Диалоги и папки используют одну полную палитру с полем оттенка, сохранёнными цветами, добавлением и очисткой. В обеих палитрах есть «Случайный» (выбирает свободный контрастный цвет) и «Пипетка» (копирует маркер с другого диалога или папки). Оба инструмента меняют текущий маркер, но не пополняют сохранённую палитру: цвет сохраняется только явным нажатием `+`. Палитра привязана к исходной кнопке и остаётся кликабельной после закрытия ПКМ-меню.
- Маркер диалога — контрастная внутренняя обводка, структурно привязанная к квадратному внутреннему контейнеру содержимого аватара без координатных расчётов, смещения и изменения геометрии строки. Высокая внешняя обёртка строки не может стать host кольца и превратить его в овал. Кольцо остаётся в локальном слое контейнера; динамический нативный индикатор Bitrix «печатает»/статус всегда рисуется поверх него и не перемещается, даже если Bitrix пересоздал индикатор с неизвестным именем класса. Нативный переключатель папок примыкает к первой строке без искусственного нижнего отступа.
- Мультивыбор обозначается только рамкой, без сплошной заливки строки.
- ПКМ по диалогу открывает нативную панель Bitrix24 по умолчанию; действия PENA встраиваются в неё.
- Панель времени — полноценное модальное окно 720×520 с реальным backdrop, focus trap, возвратом фокуса, отдельной шапкой, ссылкой отчёта и крестиком; отдельный footer не дублирует действия. Пользователь выбирает день через предыдущую/следующую дату, календарь и кнопку «Сегодня», а вкладка «7 дней» показывает статистику выбранного дня и шести предыдущих. В сводке итог расположен слева, календарный блок справа, а перерисованная круговая кнопка обновления замыкает строку; на узком экране итог остаётся первым, календарь переносится ниже. Для выбранной даты доступны ручное добавление, изменение длительности/даты и удаление отдельных записей; в прошлые дни работает только ручной ввод, таймер доступен только сегодня. Геометрия окна фиксирована относительно viewport и не прыгает при поиске или раскрытии истории. На широком экране окно делится на две равные колонки: таймер и контакты слева, ручной ввод и история справа; на узком складывается в одну колонку. Модальное окно использует browser top layer через manual popover, сохраняя DOM внутри переключателя; плашки Bitrix с высоким z-index не перекрывают его. Сводка не закреплена и прокручивается вместе с содержимым. Поле даты имеет ширину 124 px, дата центрирована в области слева от отдельного календарного индикатора с отступом 8 px. Сводка и обе колонки находятся внутри одного scroll-owner со стабильным gutter, поэтому их левые и правые края совпадают на любой ширине. Основные контролы имеют высоту 36 px, иконки — 32 px, а внутренние интервалы следуют сетке 8/16 px. Ручной ввод открыт сразу, поэтому поиск задачи и отдельные поля часов/минут не спрятаны за дополнительным кликом. В активности показаны ожидающие контакты и уже внесённое время задачи; действие «Добавить» выбирает задачу для дополнительной записи, но никаких предложенных минут расширение не рассчитывает. Открытие задачи закрывает модальное окно и возвращает место рабочему контенту. Сводка, обновление через тост, eligibility-поиск с клавиатурой и CRUD записей сохраняют единый контур без вложенных экранов. Длинные названия строк ограничены двумя строками, компактные контролы — одной; точный полный текст доступен через единый viewport-clamped tooltip мышью и клавиатурой. Длительность всегда вводит пользователь: интерфейс не предлагает минуты или часы автоматически; ноль, минуты больше 59 и значение свыше 24 часов нельзя записать. Активный или остановленный таймер можно отменить с подтверждением без создания записи. Escape сначала отменяет вложенное состояние, затем закрывает окно; крестик, сворачивание секций и двухшаговый сброс также возвращают пользователя в исходное состояние. Числовые поля не используют браузерные spin-кнопки, а пустые и заполненные значения имеют одинаковый цвет. Узкий системный scrollbar стоит справа, использует стабильный gutter и не сдвигает содержимое.
- Типографика панели времени встроена в релиз: `Onest Variable` используется для интерфейса, `Unbounded Variable` — для итоговых акцентных значений, `Consolas`/`Courier New` — для таймеров и числовых полей.
- Блок «Контакты» содержит только реальные действия с задачами с подтверждённым ALLOW_TIME_TRACKING=Y: исходящие несистемные сообщения и успешные изменения карточки, чеклиста или статуса. Обычные чаты, чтение, открытие, прокрутка, входящие сообщения и операции с трудозатратами не создают контакты. Длительность просмотра не используется. Предложения сортируются по убыванию новых контактов после последней записи и показывают учтённое время и число записей. Журнал scoped по порталу, пользователю и календарному дню; реальное сообщение в связанную задачу допустимо и при выбранном разделе «Чаты».

## Диагностика нагрузки и панели времени

- Квалифицированные контакты используют отдельный outbox `pena.timeContactOutbox.v1.<userId>.<eventId>`; timestamp/user/task неизменяемы, неизвестный день ждёт часового пояса портала. Все писатели дневного журнала берут общий Web Lock, читают свежие данные и сохраняют ID события вместе со счётчиком до ACK. Старые записи мигрируют без потери visits; предел 40 задач удалён. Пассивный просмотр не создаёт lease или heartbeat. Replay действия сериализуется дневным Web Lock и не захватывает чужой lease.
- Таймер сохраняет фактические секунды и сегменты календарных дней портала в прежнем scoped tracker key, с acknowledged ID каждой записи. Неизвестный часовой пояс останавливает запись, сохраняя исходный stoppedAt. Start/stop/cancel используют общий Web Lock и свежее чтение storage внутри него. Нулевая длительность не создаёт запись; длительность больше суток не обрезается. Неопределённый результат add не пересылается автоматически: требуется проверить журнал и явно подтвердить повтор отсутствующей записи либо отказаться от него.
- Ручное добавление хранит write intent в отдельном `${draftKey}:write-intent`, независимо от редактируемой формы. Изменение задачи/полей и сброс формы не удаляют неподтверждённую запись. Создание/разрешение intent сериализуется Web Lock, cleanup проверяет operationId; старое подтверждение не стирает новый intent. Изменение/удаление записи проверяет user scope до отправки и после ответа. Сумма после подтверждения обновляется сразу, поздний старый read не может её откатить.
- Новый CHANGED_DATE задачи инвалидирует только её elapsed-кеш; повтор строки из перекрытия delta не создаёт новых чтений. Первичный обход каталога отдельно помечает неполноту до хвоста. Интервалы свежести не являются гарантией сетевой задержки: очередь и ответ Bitrix добавляются к ним.
- Возраст elapsed-кеша отсчитывается от фактической отправки SDK-запроса (`requestedAt`), а не от постановки в очередь и не от получения ответа. Для многостраничной задачи используется самый ранний dispatch её страниц. Поэтому 15-секундный cooldown не вызывает немедленное повторное чтение только что отправленных задач, а долго отвечавший сервер не маскируется свежим временем завершения.
- «Прочитано» вызывает `im.dialog.read` без `MESSAGE_ID`, затем снимает отдельный reminder через `im.recent.unread ACTION=N`. Снятие reminder само по себе не читает сообщения. Меню переключается между «Прочитать позже» и «Снять отметку «прочитать позже»» независимо от числового unread-счётчика. Двойной клик объединяется, противоположные действия сохраняют порядок, смена пользователя блокирует позднее подтверждение. Новое сообщение за подтверждённой границей чтения остаётся непрочитанным. Ошибка снятия reminder после успешного чтения показывается как частичный результат.
- Batch использует доступный `BX.rest.callBatch` текущего/same-origin top frame, затем SDK `BX24.callBatch`. Структурированные `BX.RestError.getError()/ex` сохраняют исходный код. Пакет ограничен 50 безопасными чтениями; timeout/лимит не превращается в одиночный повтор всех запросов. Явно неподдерживаемый batch разрешает ограниченный одиночный пул. Пропущенная или повторяющаяся полная страница не считается успешной пустой страницей.
- В обоих SDK `next()` отправляет следующий запрос, поэтому адаптер читает cursor только из `answer.next` или plain numeric next. Нормализация ответа не имеет сетевых побочных эффектов. Контракт подтверждён исходниками встроенного REST-клиента и BX24 SDK; модель пяти страниц воспроизводит 15→5 транспортных запросов без потери 250 задач.
- Все REST-адаптеры расширения используют общую очередь: не более двух одновременно выполняемых запросов, интервал запуска от 80 мс, короткий запас 16 запросов и устойчивый темп два запроса в секунду. Одинаковые чтения одного scope объединяются, записи не объединяются. Таймаут и QUERY_LIMIT_EXCEEDED включают паузу 15 секунд; таймаут отсчитывается после выхода из очереди. Нативный batch сохранён, его имя в диагностике включает вложенные методы. Bitrix SDK не предоставляет отмену уже отправленного запроса; отменяется только ещё не отправленная работа, поздний ответ не применяется.
- window.__PENA_REST_DIAGNOSTICS__.snapshot() возвращает длину очереди, активные запросы, пик параллельности, число объединений и последние 200 измерений method/queuedMs/durationMs/status/code. Параметры запросов и тексты задач в журнал не попадают.
- tests/native-rest-queue.mjs проверяет ограничения, дедупликацию, отмену, таймаут и независимость записей. tests/time-functional-regression.mjs проверяет top layer под враждебным z-index, прокрутку сводки, геометрию SVG, задачу без CHAT_ID, N→Y→N, пагинацию и delta-cursor, отмену поиска и исключение скрытого времени.
- tests/artifacts/time-functional-report.json содержит фазы с длительностью и REST-диагностику; tests/artifacts/regression-summary.json — результаты всех запущенных suites и пять самых долгих. Ограничения и команды — в tests/TIME_DIAGNOSTICS.md. Это стендовые проверки, не подтверждение работы на живом портале.

## Версия и источники истины

Версия обязана совпадать в:

- `extension/manifest.json`;
- `extension/injected.js` (`VER`);
- `installers/windows/setup.iss` (`AppVersion`);
- `update.json` и его URL неизменяемого тега.

Состав runtime-релиза задаётся массивом `extension_files` в `update.json`. Папка `extension/` проверяется на точное совпадение с этим списком, поэтому бэкапы и служебные файлы не попадут в установщики.

## Правило обновления контекста

Скрипт обновляет только блок между `AUTO:BEGIN` и `AUTO:END`. Архитектурные решения и продуктовые контракты редактируются вручную в той же задаче, где меняется соответствующее поведение. Если фактический блок устарел, `-Check` завершится ошибкой.

### Проекты и единый подсчёт времени 7.5.109

- Перед первым чтением трудозатрат обязателен выбор проектов. Настройка `pena.timeProjects.v1.<portalHost>~<userId>` хранит version=1, all, ids и includeUnassigned. Не настроенный профиль не запускает time-task catalog или elapsed; существующий native chat catalog сохраняет собственные правила. «Выбрать все проекты» включает будущие доступные группы, задачи без проекта выбираются отдельно. Источник списка — `sonet_group.get`, включая доступные рабочие группы; закрытые/скрытые доступные группы не отбрасываются искусственно.
- Фильтр GROUP_ID применяется в `tasks.task.list` до пагинации и в поиске. ID-keyset остаётся монотонным. Ответ вне выбранных проектов считается ошибкой, глобального fallback нет. Полный выбранный каталог публикуется атомарно; ранние страницы и native metadata не разрешают elapsed и не расширяют его membership. Полный свежий native catalog с GROUP_ID можно использовать без повторного запроса; новый глобальный обход ради времени не запускается.
- Дата портала и полный выбранный каталог подтверждаются до первого elapsed. Открытие панели и bootstrap присоединяются к одному владельцу. Кеш, поисковые ответы и запросы ограждены portal/user, fingerprint выбора и поколением: A→B→A не принимает старый ответ A. Ручное обновление полностью сверяет выбранный каталог, затем трудозатраты, удаляя перенесённые/недоступные задачи из проекции. Ошибка не очищает подтверждённые записи.
- Периодический 10-секундный обход удалён. Pull инвалидирует конкретные задачи; закрытая панель не создаёт поток task.get на массовые события. Пропущенные новые задачи помечают каталог для scoped delta при следующем общем запуске/открытии; обычный warm open использует готовый кеш. Нативный повторный цикл после минуты может выполнить одну CHANGED_DATE-дельту выбранных проектов, затем прочитать только новые/изменённые task IDs. Курсор относится к началу запроса, с минутным перекрытием.
- Смена проектов не стирает контактный журнал, работающий таймер и неопределённые/подтверждённые операции записи. Новый Add/Start проверяет выбор повторно после ожидания. Поздний ACK другой выбранной области сохраняет операцию и контактную границу, но не добавляет её время в чужую проекцию.
- Размер окна — до 960×720 с ограничением viewport; узкий экран сохраняет одну вертикальную прокрутку. Кнопка «Проекты» открывает настройку повторно. Поиск проектов и отдельный выбор задач без проекта не запускают загрузку задач до сохранения. Ошибка записи настройки оставляет форму и предыдущий выбор.
- Добавлены suites `time-project-scope`, `time-project-layout`, `time-project-settings-ui`. Integrated startup дополнен тем же порталом из 4149 задач с 149 задачами выбранного проекта: проверяются ровно 3 scoped страницы, 149 уникальных elapsed и отсутствие повторного подсчёта при первом открытии. Отчёты лежат в `tests/artifacts/`; это управляемый Chromium/SDK стенд, не живой Bitrix24.
- Нулевой cursor означает первую загрузку, а не устаревший каталог: bootstrap разрешает delta только для уже подтверждённой текущей области проектов. Поэтому после native-прохода первый подсчёт повторно использует полный свежий каталог. Поиск может работать раньше его завершения, но новые записи и запуск таймера доступны только после подтверждения выбранной задачи; восстановление уже начатой записи сохраняется.
- Явно выбранные «все проекты» вместе с задачами без проекта используют общий full-владелец `_syncDialogTaskCatalog` в любом порядке запуска native/time. Подтверждённые строки передаются в область времени атомарно; неполный или устаревший по поколению результат не вызывает запасной повторный обход. Каталог отдельных проектов и delta продолжают применять серверный фильтр `GROUP_ID`.
- Область времени строится по host и подтверждённому текущему пользователю (`_getDialogTimeIdentityScopeKey`), включая ответ `user.current`, даже пока Messenger не опубликовал native identity. Настройки проектов, поиск, блокировки и проверки поздних ACK используют эту область. Общий native full-каталог допустим только при непустом совпадении native/time identity; при отсутствии native identity явное открытие панели читает выбранный каталог самостоятельно, не запускает native startup и не использует чужой каталог.

### Общий запуск и стоимость отрисовки панели времени 7.5.105

- Первый elapsed-запрос ждёт подтверждённой даты портала. Если ранняя страница каталога появилась до `server.time`, выбранный предварительный «сегодня» или недельный диапазон переводится на день портала до вычисления ключа кеша; явная историческая дата сохраняется. После ожидания повторно проверяются scope, видимость и открытая панель/владелец bootstrap. При известной дате дополнительных ожиданий и запросов нет.

- Часы общего тестового портала и исходные elapsed-записи согласованы по UTC+03:00 независимо от часового пояса компьютера. Model-проверка покрывает границу суток, а contact-assertions проверяют точный день портала. Для воспроизведения CI браузерных проверок доступен `PENA_TEST_BROWSER_TIMEZONE=UTC`.

- После завершения нативной попытки и освобождения её visual guard запускается один scoped цикл сегодняшнего времени. Он присоединяется к общему полному task-каталогу, затем читает недостающие трудозатраты. В стандартном нативном виде и при отмене прокрутки пользовательским вводом метаданные также загружаются: подтверждение полноты DOM не является условием чтения времени и не подменяется API-каталогом. Если физическая лента не требовала API-индекса, цикл запрашивает его один раз. Открытие панели во время запуска присоединяется к той же работе. Прогресс трудозатрат не удерживает нативный overlay и не блокирует Messenger.
- Полный каталог имеет одного владельца на scope; запрос головы присоединяется к уже идущему полному чтению. Голова не заменяет владельца полного прохода. После подтверждения первого курсора немедленная повторная дельта не нужна. Hide/offline отменяет принятие поздних ответов; следующий общий reconcile продолжает недостающее. Ошибка или неполный каталог не подтверждают пустой день.
- Сегодняшняя сумма обновляется в кнопке и при закрытой панели во время общего цикла. Обычные события и квалифицированные контакты только помечают конкретные задачи изменёнными; открытая панель либо следующий общий reconcile читает их точечно. Сам секундный тик таймера не читает каталог и не перестраивает панель.
- Если полночь наступила во время чтения, одновременный wake ждёт старого владельца и запускает один цикл нового дня. Ответы прежней даты не подтверждают новый день. Смена пользователя и потеря активного Messenger проверяются между волнами, а не только при запуске; старый ответ не снимает владельца нового scope.
- Таймер расположен последним блоком на всю ширину. Ручное добавление и таймер имеют независимые поля поиска и выбора задачи. Результаты ограничены видимыми подсказками; тысячи option больше не строятся при каждом обновлении. Изменение ручной формы не переключает выбранную задачу таймера.
- Журнал сначала показывает 50 записей, кнопка «Показать ещё» добавляет следующую порцию из готового снимка без REST. Итоги и контакты считаются по всем записям. Неизменившиеся строки переиспользуются; открытый редактор и введённое значение сохраняются при поступлении новой записи. Закрытая панель не пересобирает скрытый журнал.
- Пакетное принятие заменяет только проверенные задачи в агрегате, сохраняя неизменённые объекты и границы контактов. Построение рабочего набора использует Set вместо квадратичных includes. Полнота дополнительно проверяется в конце с учётом новых ID и ревизий.
- Начальная строка последовательно сообщает «Загружаем список задач» и «Считаем время». После готовности она освобождает место; точечные фоновые изменения не показывают постоянную загрузку. window.__PENA_TIME_LOAD_DIAGNOSTICS__.snapshot() раскрывает фазу общего цикла, дату, количество принятых задач и страниц, ошибку; тексты задач не журналируются.
- Новые suites: time-snapshot-performance-regression, time-tracker-search-regression, native-startup-time-contention. Последняя совмещает реальную нативную материализацию, 4149 API-задач, 321 запись и ввод в Chromium; отдельно проверяет готовый сегодняшний снимок до первого открытия панели. Это контролируемый стенд, не живой Bitrix.

### Снимки трудозатрат и повторные контакты 7.5.101

- Возраст задачи больше не запускает повторное чтение elapsed. Снимок подтверждён до явной инвалидации; `CHANGED_DATE`, события задач, квалифицированные контакты и собственные изменения дают новые ревизии. Периодическая дельта каталога остаётся лёгкой проверкой изменений и не превращается в повтор всех трудозатрат. Пустые и недоступные ответы различаются; отказ доступа не объявляет задачу проверенной пустой.
- Первый проход охватывает весь рабочий набор; начальные приоритетные ответы не являются доказательством полноты. `hasVerifiedData` разрешает показ подтверждённых чисел, `hasCompleteSnapshot` отдельно подтверждает завершённый диапазон и полный каталог своей области. Последний признак сохраняется при последующих точечных проверках. Пустой завершённый каталог явно подтверждает 0/0.
- Одновременные ручные обновления объединяются; ручное нажатие во время первого полного прохода присоединяется к нему. Один объединённый завершающий проход добирает изменившиеся задачи, включая событие после принятия их страницы. Закрытие прекращает дальнейшие волны, повторное открытие продолжает непроверенную часть. После вытеснения из кеша восьми периодов или перезапуска документа нужен новый первоначальный проход.
- Строка статуса видна при неполном первом чтении, ручном обновлении и ошибке. Готовый снимок и его точечная фоновая проверка не показывают строку и не занимают под неё место. Реальное массовое изменение более одного пакета (50 задач) показывает «Обновляем изменённые задачи». Кнопка ручного обновления и часы остаются статичными. При ошибке сохранённые значения остаются видимыми.
- Подтверждённый новый контакт инвалидирует только свою задачу после успешной записи квалифицированного события; дубликат, входящее сообщение, heartbeat и неквалифицированное открытие не дают этого повода. Закрытая панель только запоминает ревизию; при видимой панели события объединяются в одно точечное чтение. Старый callback другой области не отправляет запрос.
- Контакты показывают остаток после успешного внесения и уже учтённую длительность дня. Повторная активность возвращает карточку; ранее учтённые контакты не включаются в новый счётчик. Граница относится к отправке записи, а не к позднему ACK или рабочему `CREATED_DATE`. Изменение/удаление длительности не поглощает новые контакты. Внешний `DATE_START` с явным часовым поясом допустим как время внесения; локальный подтверждённый ID и неизменяемая граница имеют приоритет. При неизвестном времени внешней записи контакты сохраняются.
- Большой API-стенд отдельно моделирует 4149 задач и проход длиннее прежнего TTL; браузерный стенд отдельно проверяет видимые состояния на 30 задачах. Результаты не выдаются за замер живого Bitrix. Обзор изменений и ограничений: `tests/TIME_SNAPSHOT_CONTACTS_v7.5.101.md`.

### Предыдущая итерация обратной связи 7.5.99

- Признак `hasVerifiedData` отличает подтверждённые данные от предварительного `aggregate([])`. Только принятый ответ журнала, положительный ACK или завершённый пустой каталог своей области подтверждают значение. До этого во всех представлениях виден прочерк; проверенный ноль сохраняется при загрузке и ошибке. Синтетический ноль не становится результатом только из-за наличия объекта кеша.
- Кнопка ручного обновления и часы не вращаются при фоновых чтениях. Две дуги SVG имеют одинаковую геометрию с поворотом на 180 градусов. Кнопка блокируется только на время собственной ручной операции; повторные клики объединяются. Уведомление завершения привязано к пользователю, выбранному диапазону и открытой панели.
- Под сводкой постоянно зарезервирована строка статуса высотой 24 px. Начальная загрузка, фоновая проверка, неполные данные и ошибка различаются явно; уже известные суммы и записи остаются на экране. Прогресс отражает текущую проверку, а не старое покрытие кеша. При неизвестном объёме работает отдельный неопределённый индикатор с поддержкой reduced motion. Фоновые проверки не озвучиваются через aria-live. До ответа API отсутствие данных не показывается как нулевое время или отсутствие записей.
- Живой ручной write intent сохраняет состояние sending только при совпадении operationId и scoped storage key с активной операцией. После перезапуска незавершённый intent остаётся unknown: автоматический повтор ADD запрещён. Текущая отправка не показывает предупреждение о потерянном ответе, реальный отказ записи не называется ошибкой чтения.
- Положительный ACK с ID сразу обновляет суммы и освобождает форму. Вспомогательная отметка контакта выполняется отдельно; её ошибка сообщает, что время уже сохранено, и не разрешает повторную отправку той же записи. Свежий полный снимок изменённой задачи после ADD сохраняет исходный timestamp чтения, поэтому лишний GET не запускается и TTL не продлевается. Неполные, устаревшие и инвалидированные событиями снимки продолжают перечитываться. Принудительный ответ сервера остаётся источником истины; искусственное отставание реплики не скрывается бессрочным локальным слоем.
- Секундный тик активного таймера обновляет только краткую длительность в кнопке и панели. Неизменившийся текст повторно не записывается, скрытая страница не выполняет DOM-работу. Смена дня, пользователя или задачи запускает одну полную синхронизацию; внешняя остановка прекращает интервал. Каталог, история и форма не пересобираются каждую секунду.
- Новые suites: time-clock-performance, time-panel-ui и time-panel-feedback. Последний проверяет настоящие обработчики в Chromium с управляемыми задержками SDK; это не измерение живого портала. Контракты контактов, времени и неопределённого исхода записи сохранены.
- Тест ручного timeout начинает инъекцию только после завершённого каталога и освобождения очереди; проверка и клик выполняются атомарно. Отдельно проверяется ошибка уже работающего фонового запроса: ручной преемник ждёт cooldown, сохраняет сумму и сообщает собственный результат. Ошибку предшественника нельзя считать ошибкой успешного ручного обновления.

### Изоляция поиска и фоновой работы 7.5.96

- Поиск PENA принадлежит только нативной шапке соответствующего списка. Глобальные fallback по placeholder «Поиск сотрудников»/«Поиск задач» недопустимы: отсутствие или пересоздание шапки не даёт права перехватывать поля entity-selector и упоминаний. Поздняя шапка подхватывается после mount; переиспользованное поле вне нативного владельца перестаёт считаться поиском PENA.
- При известной подключённой шапке toolbar observer проверяет принадлежность изменений к ней до обходов поддеревьев. Lifecycle observer допускает одну проверку пакета мутаций: добавленные узлы одного ограниченного контейнера проверяются совместно, удаление сверяется с сохранёнными ссылками источников. Поздний скрытый список, вложенный новый source и удалённый предок активного списка сохраняют прежний lifecycle-контракт.
- Загрузка названий времени не использует просроченную eligibility как повод перечитать известное название. Недостающие названия загружаются пакетно; перед отправкой, применением ответа и повтором проверяются scope, видимость и открытая панель. Отмена не помечает неотправленные ID проверенными. Свежая проверка ALLOW_TIME_TRACKING перед новым контактом или записью времени остаётся обязательной.
- Кандидаты времени используют каноническое название без обхода контролируемых диалогов. Fallback названий и CHAT_ID индексируется один раз на перерисовку; эти индексы не переживают вызов и не скрывают новые данные отрицательным кешем. Состав и порядок результата сохраняются.
- Запись каталога в repository выполняется один раз на scope одновременно. Повторный callback присоединяется к текущей записи; новые dirty-версии и full revision запускают один следующий проход после подтверждения. Ошибка сохраняет данные и существующий backoff; подтверждение старого scope не изменяет новое состояние, включая переход пользователя A→B→A.
- `native-mention-interference-regression.mjs` сравнивает настоящий локальный HTTP и следующий кадр при CPU ×4, истории из 4000 элементов и popup на 240 строк. Отрицательный контроль обязан выявлять блокировку потока. Это контролируемая модель нативного селектора, а не живая проверка пользовательского портала. Отчёт аудита: `tests/NATIVE_INTERACTION_AUDIT_v7.5.96.md`.

### Уточнения проверки контактов и фоновой синхронизации

- Перед сохранением квалифицированного контакта выполняется свежий tasks.task.get: старые Y/N после потерянного события не считаются окончательным решением.
- Оптимистическая запись после add использует ID из ответа Bitrix; временный ID нельзя отправить в update/delete. Принудительное чтение после изменения ждёт старое чтение и выполняет один объединённый повтор.
- Фоновый REST-аудит готового нативного списка не ждёт подробности всех закреплённых диалогов; ручное обновление повторяет только непроверенный/запрещённый доступ и ранее незавершённую загрузку preview. Материализация сохраняет отдельный контракт. При исправлении старых личных ID названия сравниваются с API-каталогом, а не переиспользованной DOM-подписью.
- tests/artifacts/native-scenarios.json содержит отдельные сценарии большого нативного набора с длительностями и REST-диагностикой; recent-failure-*.json содержит снимок упавшего сценария синхронизации.
- Релизный workflow сохраняет JSON/PNG-диагностику и при падении тестов. Сценарий resume пишет resume-failure.json; после закрытия панели отдельно проверяет восстановленный scroll-anchor и отрисовку переиспользуемой строки.
- Проверка доступности исчезнувшего tail-anchor использует сам сохранённый ID, а не REST-alias из метаданных переиспользованной строки. Диагностика materialization показывает tailIds; упавший нативный сценарий сохраняет полное состояние загрузки вместе с REST-замерами.
- Tail-anchors фиксируются непосредственно на подтверждённом физическом дне до commit/восстановления viewport. Для абсолютных виртуальных строк используются их native inline-transform/top: CSS-фильтр может обнулить bounding rect и computed transform, а порядок DOM/сохранённые ранги отражать сортировку PENA. Тесты проверяют все пять физически последних ID после каждого восстановления и переключения режима.
- Resume-стенд откладывает виртуальный render скрытого режима до его показа: trailing scroll/RAF с нулевой геометрией не должен портить пул при сохранённом scrollTop. Проверка повторного сохранения таймера ждёт завершения запроса и разблокировки кнопки, а не промежуточной надписи «Повторить».

### Автозагрузка и оптимизация 7.5.91

- Первый видимый нативный source автоматически догружается до физически подтверждённого хвоста. Скрытая вкладка ждёт своего открытия; все существующие fences, ограниченные retry и восстановление якоря сохраняются. `__PENA_TEST_SKIP_INITIAL_MOUNT__` изолирует стартовый обход только в тестах горячего пути.
- Объединение нативного порядка использует линейный проход для уникальных ID; неоднозначные дубликаты сохраняют прежнее правило. Метаданные и цвет каждой строки вычисляются один раз на сортировку, без долгоживущего кэша. 1000 детерминированных случайных окон сверяются с независимой спецификацией.
- Каталог времени обновляет elapsed working set на первой странице и хвосте, без повторов на промежуточных страницах; неизменившаяся delta не перерисовывает результаты поиска. Если новые eligible ID пришли во время чтения времени, выполняется один объединённый повтор после завершения старого чтения.
- Основа оптимизации: ограниченная работа на главном потоке и отделение вычислений от DOM-записей: https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing ; существующая REST-пагинация: https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-list.html .

### Снижение нагрузки при обычной работе 7.5.93

- Нативные отправка сообщения и открытие задачи не проходят через очередь PENA. Найденные фоновые запросы и работа DOM могут конкурировать с ними за ресурсы; это не доказательство конкретной пятисекундной задержки на живом портале.
- События задач при закрытой или скрытой панели времени только инвалидируют локальную eligibility. Отложенный `tasks.task.get` запускается для видимой панели; scope, ревизия задачи и видимость перепроверяются перед постановкой и отправкой запроса. Квалификация контакта сохраняет обязательную свежую проверку Y/N.
- Полный task-аудит и полный/delta-каталог времени обходятся по `ID asc`, с `filter['>ID']` последнего полученного ID и `start=0` на каждой странице. Удаление ранее прочитанной задачи и смена ACTIVITY_DATE не сдвигают непрочитанную строку за offset. Немонотонный ответ останавливает проход без продвижения watermark. Короткое чтение головы сохраняет ACTIVITY_DATE и никогда не подтверждает общий полный cursor. Полный проверенный аудит передаёт каталогу времени cursor начала запроса, поэтому открытие панели использует delta с перекрытием 60 секунд, не повторяя весь обход.
- Пакетное чтение разрешено только для перечисленных read-методов. Таймаут, сетевой сбой и ограничения API не запускают повтор всей пачки отдельными запросами. Частичные ответы сохраняются; повторяются только неуспешные временные чтения. Individual fallback допустим только при отсутствии/явно неподдерживаемом batch SDK, ограничен двумя запросами и прекращает выдачу после ошибки. `OPERATION_TIME_LIMIT` включает существующую паузу очереди 15 секунд; это локальная защита, не чтение серверного `operating_reset_at`.
- Неизменённые классы/текст строк, слоёв аватара и таймера повторно не записываются. Служебные атрибуты PENA не запускают поиск нативного source. Обычный жест вне списка не перебирает все его строки. При отсутствии шапки её поиск повторяется только по релевантному добавленному узлу; поздний mount сохраняется. Ожидание Messenger в content.js не сканирует весь документ при каждом изменении задачи/CRM; worker health сравнивается с текущим manifest, включая имя entrypoint.
- Наблюдатель маршрутов хранит ссылки на известные нативные списки, включая скрытые. Изменения классов/видимости проверяются через принадлежность и предков этих списков без поиска по поддереву истории сообщений; структурные изменения обновляют набор, удалённые источники освобождаются. Переключение скрытого списка и замена source остаются полноценными событиями lifecycle.
- Дополнительные обязательные suites: `network-idle`, `task-keyset`, `native-batch-backpressure`, `native-dom-mutation` и `interaction-contention`. Последний измеряет событие, обработчик, настоящий HTTP и следующий кадр в одинаковых включённом/выключенном сценариях с CPU ×4; synthetic SDK и backend не подменяют проверку установленного Bitrix. Общий отчёт хеширует весь runtime и сохраняет длительности и ошибки каждого набора. Счётчики запросов/мутаций и скорость отдельного observer нельзя выдавать за такое же ускорение всего приложения.
- Протокол A/B использует одинаковое число завершённых действий: по 24 на старте и после успокоения lifecycle в каждом плече. Наследованный от recovery-стенда 16-миллисекундный опрос геометрии здесь отключён; собственный RAF только записывает время. Бюджеты HTTP и следующего кадра проверяются отдельно для старта и обычной работы, а также по всей выборке. Неуспешные прогоны сохраняются вместе с диагностикой, а не заменяются успешным повтором без анализа.
