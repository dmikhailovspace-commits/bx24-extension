## Назначение

Расширение запускается внутри Chromium-оболочки настольного Bitrix24 и дополняет нативный список чатов папками, поиском, фильтрами, сортировкой, мультивыбором и цветовыми маркерами. Основной принцип — не подменять верстку Bitrix24 собственным каталогом без необходимости.

## Архитектура

- `extension/content.js` проверяет цельность установленного релиза и последовательно внедряет runtime-модули в страницу.
- `extension/injected.js` управляет интерфейсом, загрузкой диалогов, сортировкой, папками, поиском и интеграцией с нативным DOM Bitrix24.
- `extension/native-*.js` содержат изолированные модели каталога, состояния взаимодействия, времени и жизненного цикла.
- `extension/dialog-repository.js` — клиентский мост к хранилищу.
- `extension/background.js` — service worker с каталогом диалогов в `chrome.storage.local`.
- `.github/workflows/build-macos.yml` — единственный удалённый путь выпуска macOS DMG: сборка и проверка выполняются на GitHub-hosted `macos-15`.
- Область каталога: `portalHost~userId`. Запрос страницы принимается только при совпадении `portalHost` с origin.
- Репозиторий использует schema v2: `revision`/`baseRevision`, идемпотентный `operationId`, persistent lease fence и CAS-цикл `get → merge → retry`. Подтверждённый полный снимок удаляет только записи, которые существовали в его базовой ревизии и получили явный tombstone; новая запись другой вкладки при конфликте сохраняется. Ошибка worker/storage не отключает репозиторий: dirty-очередь ждёт reconnect и повторяет запись. Поздний reconnect не делает blind restore: remote snapshot объединяется с живыми dirty-записями по base revision и свежести, поэтому собранные без worker ID не теряются, а старые tombstone не возвращаются.

## Продуктовые контракты

- Нативная лента и нативный scrollbar Bitrix24 должны сохраняться. Нельзя допускать скачков прокрутки или принудительного смещения экрана.
- Нативный режим — единственный рабочий режим. Значение `pena.dialogControlNative.v1.*=0`, оставшееся от удалённого каталога, автоматически мигрирует в `1`; старый флаг не может скрыть папки, сортировку или панель времени на обновлённом профиле.
- По умолчанию сортировка — по дате, новые сверху. Каталог загружается динамически до фактического конца, без лимитов 100 или 500 диалогов.
- Состояние каждого режима разделено на `catalog`, `materialization` и `attempt`. Метаданные репозитория не могут объявить нативный DOM готовым, а ошибка отдельной попытки не портит последний подтверждённый каталог.
- Один дедуплицированный reconcile запускается при первом появлении Messenger, смене режима/source, `resume`, `pageshow.persisted`, долгом возврате видимости, `focus`, `online` и скачке heartbeat-таймера. Долгая пауза — `resume/pageshow.persisted`, скачок от двух минут или скрытие дольше 15 минут. Обычный focus, resize и короткое сворачивание не запускают прокрутку.
- DOM-материализация не имеет TTL. После долгой паузы reconcile проверяет source-generation, диапазон, head-сигнатуру и пять хвостовых ID. Хвост проверяется коротким bottom-probe под общим visual guard с восстановлением ID-якоря и пиксельного смещения. Успех требует 5/5 ID; каждый отсутствующий ID проверяется через API, и полный проход не нужен только если все пропуски подтверждены как недоступные. Любой всё ещё доступный хвостовой ID, смена source или схлопнувшийся диапазон запускают ровно один полный native-scroll под overlay.
- Полный проход не принимает `idle` или временно неподвижный `scrollTop` как доказательство конца: viewport обязан физически достичь `maxTop`, после чего нужны две стабильные нижние выборки, неизменная source-generation, отсутствие loader Bitrix и не меньше диалогов, чем в прошлом подтверждённом поколении. До 20 пропавших ID проверяются с concurrency 2. Freeze/hidden приостанавливают проход и его active-time timeout; смена режима/source аннулирует старую попытку. Ошибка, offline или timeout сохраняют предыдущий каталог и ставят retry 1/2/5/15/30/60 секунд; `online` будит восстановление сразу.
- У холодного поколения есть дополнительное доказательство ожидаемого набора ID. Schema-v2 snapshot с явным `confirmedIds` служит только нижней границей и быстрым bootstrap: он может устареть по новым диалогам и сам по себе не подтверждает текущее поколение. `ready` холодного source требует свежего полного fenced API-аудита, после чего нативный проход обязан физически встретить каждый ожидаемый ID; дополнительные нативные ID разрешены и не удаляются. При offline сохраняется последний каталог и ставится retry, но текущее поколение не получает ложный `ready`. Первый пустой ответ API не доказывает пустой каталог, особенно если текущий native-source уже содержит строки. Пропавшие ожидаемые ID сначала проверяются по доступности и только подтверждённые tombstone исключаются из доказательства.
- Полный API-аудит привязан к portal/user/mode, schema, source-generation и identity нативного source. Запоздалый результат после смены пользователя, режима или source отбрасывается. Его метаданные объединяются с live-состоянием по свежести сообщения, счётчиков и availability; старый аудит не может откатить более новое сообщение, дату, непрочитанное или tombstone ни в общем каталоге, ни в снимке текущего прохода. Новый live ID, пришедший в середине прохода, сохраняется metadata-only, но не добавляется в `seen`/`confirmedIds`, пока его физически не показал нативный source.
- Индекс task-чатов одновременно загружается через постраничный `tasks.task.list` по 50 задач, но не удерживает loader и публикуется только после завершения нативного прохода, чтобы параллельные записи не перетирали друг друга. Он связывает задачи с чатами по `CHAT_ID`; дата сортировки старой задачи берётся из последнего сообщения, иначе из `ACTIVITY`/`CHANGED_DATE`. API-индекс не считается доказательством полноты task-ленты. При первом переходе в «Чаты задач» текущего документа нативный проход запускается один раз; последующие переключения используют материализованный источник, пока Bitrix сам его не заменит или не сбросит.

- Запрещён кэшированный replacement/continuity-список: расширение не создаёт собственные строки вместо строк Bitrix и не определяет полноту по числу элементов виртуального DOM. Для режима сохраняются identity списка/viewport, source-generation, диапазон, подтверждённый полный набор ID, пять head/tail ID и доверенная пользовательская позиция. Эти данные нужны только для проверки и восстановления нативного источника, а не для подмены его отрисовки.
- `im.recent.list` остаётся источником метаданных для совместимости, тестов и фонового обновления головы, но не считается доказательством, что старые строки появились в оригинальной ленте. Его пагинация использует `LIMIT=200`: явный валидный `next` имеет приоритет, без него `OFFSET` растёт на запрошенный `LIMIT`, а не на число строк в схлопнувшейся странице. Пересечения дедуплицируются; нулевой или заниженный `total` служит только прогрессом и не обрывает проход. `tasks.task.list` следует явному `next`; без него полная страница продолжает `START += 50`, а короткая страница является документированным хвостом.
- Таймаут лёгкой фоновой проверки головы не заменяет готовый атомарный каталог ошибкой и не запускает вслед за собой второй медленный `im.recent.list`; проверка тихо откладывается до следующего окна свежести. Жёсткая ошибка полной загрузки всегда имеет приоритет над остаточным счётчиком. Если не подтверждён именно сохранённый папочный диалог, статус и подсказка показывают его название и ID, а не безымянное «Не загружено: 1».
- Синхронизация разделена по стоимости: голова `im.recent.list` — 1 минута, task-индекс — 15 минут, полный REST-аудит метаданных — 24 часа. API-курсор и время полного API-аудита хранятся отдельными versioned watermarks; время записи кэша, нативного прохода или visible-window merge ими не является. Старый manifest без явного API-watermark после обновления получает курсор `0` и проходит один полный аудит. Курсор полного аудита фиксируется в момент его старта, чтобы следующая дельта не пропустила события, пришедшие во время пагинации. Фоновые проверки работают только через API, никогда не прокручивают реальный viewport и не показывают loader. REST может добавлять и обновлять записи, но не объявляет DOM материализованным, не отменяет native-scroll и не удаляет записи по неполному ответу.
- Поиск, активная папка, сортировка, маркеры и per-mode scroll-anchor переживают probe/recovery без сброса. Восстановление не имеет права показывать диалог из другой папки, создавать replacement-строки, скрывать нативный scrollbar или оставлять viewport в служебной позиции.
- Уменьшение `scrollHeight`, вызванное собственной фильтрацией PENA через `display:none`, относится только к presentation-слою и не инвалидирует уже подтверждённую materialization того же source-generation. Реальное схлопывание источника после долгой паузы проверяет tail-probe: он временно раскрывает нативные строки, сверяет физический диапазон и сохранённые хвостовые ID. Отложенный `initial-mount`/`source-ready` timer не должен запускать второй полный проход из-за активной папки, поиска или фильтра.
- После `ready` Bitrix может переиспользовать небольшой пул DOM-строк и показать более старые ID только при ручном движении вниз. Такое recycled-окно немедленно получает текущие папку, поиск, маркеры и сортировку, даже если параллельно идёт REST-аудит. Ранг новых нижних ID продолжается после максимального подтверждённого `nativeRecentRank`, а не начинается локально с нуля. Полный проход подтверждает низ семью стабильными выборками примерно за 1,1 секунды; любая поздняя строка или изменение диапазона сбрасывает это подтверждение, включается в materialization и не меняет пользовательский scroll-anchor.
- Фоновый REST-аудит и detail-обогащение могут заменить синтетическую дату реальной датой сообщения, но не имеют права стирать доказанный `nativeRecentRank`. Иначе поздняя строка сначала попадает в текущую сортировку, а после атомарного REST-коммита перемещается в неверную часть ленты. Regression-сценарий трижды переназначает ID одного пула и проверяет оба направления сортировки до, во время и после медленного REST-аудита при неизменном scroll-anchor.
- Loader один для всех режимов: `Прогрузка диалогов`, линия и числовой процент без поясняющего текста. Даже до первого измерения показывается числовое `0%`, а не точки; затем используется фактическое отношение или оценка прогресса. Loader перекрывает всю панель, следует за её размером и используется только при первой материализации режима в текущем документе, ручном полном обновлении или восстановлении неполного/несовместимого состояния. Он не закрывается по времени: `ready` выставляется только после подтверждённого стабильного конца нативной ленты. Фокус, разворачивание окна, resize, фоновая дельта и тихое обновление просроченного снимка не показывают loader. Пока холодный нативный проход не завершён, массовая проверка отдельных папочных диалогов не запускается: это исключает сотни параллельных REST-запросов и не мешает трекингу времени. Фоновый task-индекс не блокирует интерфейс. Компактный статус после успешной загрузки скрыт.
- При включённом расширении поле поиска визуально остаётся нативным, но поиск Bitrix отключён: события перехватывает отдельный поток PENA. Запрос хранится независимо, не сбрасывается при открытии диалога или клике вне строки, а очистка возвращает полный список. Автофокус Bitrix при запуске снимается; реальный клик пользователя по строке поиска сохраняет фокус. Фильтрация не удаляет нативную верстку и цветовой маркер строки.
- Папки не заменяют нативные строки. Диалоги внутри папки обязаны оставаться доступными фильтрации и сортировке.
- Пользовательскую папку можно drag-and-drop перенести с вкладки «Все» или из другой группы на вкладку целевой группы; вложенные диалоги перемещаются вместе с ней. Системная вкладка «Все папки» не перетаскивается.
- Цвет назначается только диалогу, состоящему в папке. При удалении из папки цвет и контроль маркера удаляются.
- Диалоги и папки используют одну полную палитру с полем оттенка, сохранёнными цветами, добавлением и очисткой. Палитра привязана к исходной кнопке и остаётся кликабельной после закрытия ПКМ-меню.
- Маркер диалога — контрастная внутренняя обводка, структурно привязанная к нативному контейнеру аватара без координатных расчётов, смещения и изменения геометрии строки.
- Мультивыбор обозначается только рамкой, без сплошной заливки строки.
- ПКМ по диалогу открывает нативную панель Bitrix24 по умолчанию; действия PENA встраиваются в неё.
- Панель времени — единый компактный дневной центр с отдельной шапкой окна и крестиком, сводкой за сегодня, таймером, активностью, ручным вводом и раскрываемой историей в этом порядке. Обновление остаётся внутри сводки, а его успех или ошибка показываются коротким тостом и не создают постоянный дублирующий блок. Селект таймера содержит только реальные названия доступных задач без служебных пунктов; если подходящих задач пока нет, это показывается отдельным состоянием вне списка. В ручном вводе нет рекомендаций и предвыбранной задачи: поиск сначала мгновенно фильтрует уже загруженный task-каталог, затем дополняет выдачу через `tasks.task.list`; серверный `ALLOW_TIME_TRACKING` не используется как поисковый фильтр, а пригодность результата проверяется на клиенте. Поэтому поиск продолжает работать при несовместимом или временно недоступном REST. Выдача занимает место в потоке формы и не перекрывает поля часов и минут. Чтение затраченного времени безопасно повторяется после единичного сетевого или временного сбоя Bitrix. Новое время записывается через `task.elapseditem.add`, а записи удаляются из той же панели через `task.elapseditem.delete` с компактным двухшаговым подтверждением. После ошибки сохранения таймера пользователь может повторить запись или двухшагово сбросить несохранённый интервал и вернуться к исходному выбору задачи; корректировка оценки имеет отдельную отмену без записи. У всех всплывающих и вложенных рабочих состояний есть явный возврат или закрытие. Числовые поля не используют браузерные spin-кнопки, а пустые и заполненные значения часов и минут имеют одинаковый цвет. Узкий системный scrollbar стоит справа, использует стабильный gutter и не сдвигает содержимое.
- Типографика панели времени встроена в релиз: `Onest Variable` используется для интерфейса, `Unbounded Variable` — для итоговых акцентных значений, `Consolas`/`Courier New` — для таймеров и числовых полей.
- Блок «Активность» строится только из задач и диалогов раздела «Чаты задач», у которых Bitrix возвращает `ALLOW_TIME_TRACKING=Y`. Обычные чаты, задачи с выключенным учётом времени и устаревшие записи без `taskId` не создают касаний, не получают оценку и не показываются в дневной истории. Открытие задачи или task-чата только запускает сессию и само по себе не считается работой. Касание квалифицируется один раз после 60 секунд активного просмотра либо сразу после подтверждённого исходящего сообщения текущего пользователя в task-чате; повторные события одного действия в пределах 15 секунд дедуплицируются. Фоновый тик раз в 5 секунд аккумулирует только фактический открытый интервал, повторное закрытие не добавляет время, а непрерывный простой ограничен 15 минутами. Касания остаются контекстным счётчиком, но не добавляют выдуманные минуты; оценка активного времени округляется вверх до 5 минут и записывается только по явному действию пользователя. После записи сохраняется граница уже учтённых активных секунд, поэтому следующая оценка включает только новый интервал и не дублирует ранее сохранённое время. История хранится локально в разрезе портала, пользователя и даты. Открытая панель и введённые данные сохраняют свой DOM при фоновом обновлении нативного переключателя, чтобы исключить мигание и потерю фокуса.

## Структура

```text
.github/workflows/  нативная сборка macOS через GitHub Actions
extension/          единственный источник runtime-файлов расширения
  icons/            иконки расширения
  fonts/            локальные variable-шрифты панели времени
installers/
  windows/          build.bat, setup.iss, updater и launcher
  macos/            build.sh, GUI installer, Universal native launcher и updater.sh
tests/              тесты моделей, DOM-harness и release integrity
tools/              обслуживание контекста и структуры
dist/               только установщики текущей версии
guide.html          пользовательская инструкция
README.md           краткая установка и команды разработчика
update.json         состав и адрес неизменяемого релиза
```

`node_modules/` — восстанавливаемая локальная зависимость, не часть исходной структуры. Резервные копии, временные файлы и старые установщики в репозитории не хранятся.

## Версия и источники истины

Версия обязана совпадать в:

- `extension/manifest.json`;
- `extension/injected.js` (`VER`);
- `installers/windows/setup.iss` (`AppVersion`);
- `update.json` и его URL неизменяемого тега.

Состав runtime-релиза задаётся массивом `extension_files` в `update.json`. Папка `extension/` проверяется на точное совпадение с этим списком, поэтому бэкапы и служебные файлы не попадут в установщики.

## Проверка и выпуск

1. Запустить `pnpm test`; успешный результат — 15/15. Новый resume-recovery suite использует постоянный `scrollHeight` и пул из 24 переиспользуемых строк; критерий полноты — точный набор ID, доступность самого старого диалога и сохранённый scroll-anchor, а не число DOM-узлов или внутренний флаг.
2. Запустить `tools/update-project-context.ps1 -Check`.
3. Отправить проверенный source commit в `dmikhailovspace-commits/bx24-extension` и создать тег версии `v*`. Единственный release workflow сначала на `windows-2025` выполняет полный `pnpm test` и context check; обе сборки зависят от этого source gate.
4. Тот же workflow собирает Windows EXE на `windows-2025` и Universal macOS DMG на `macos-15`, сверяет их SHA-256 и публикует в GitHub Release ровно четыре явно названных файла: два артефакта и два sidecar. Все используемые GitHub Actions закреплены полными commit SHA.
5. macOS job использует Go 1.26.7 для минимальной macOS 12, вызывает `installers/macos/build.sh`, затем проверяет `hdiutil verify`, `plutil`, срезы `x86_64 + arm64` обоих launcher-файлов, minimum OS, executable modes, единственный видимый `.app` и отсутствие CRLF. Локальная кросс-сборка DMG на Windows не является релизным артефактом; в `dist/` принимается только образ из зелёного workflow с совпавшим SHA-256 sidecar.
6. Проверить SHA-256 обоих артефактов и убедиться, что в `dist/` осталась только текущая версия.
7. macOS DMG — UDZO/HFS+ образ с одним видимым `PENA BX24 Installer.app`. Установщик и создаваемое им приложение запускаются через Universal Mach-O launcher с двумя срезами `x86_64` и `arm64`; shell-скрипты лежат только в Resources и никогда не являются entry point приложения. Установка и выбор Bitrix24 идут через системные GUI-диалоги без Terminal. Workflow доказывает нативную сборку и статическую проверку на macOS, но живой GUI-запуск следует подтверждать отдельно; образ не подписан и не notarized.

## Правило обновления контекста

Скрипт обновляет только блок между `AUTO:BEGIN` и `AUTO:END`. Архитектурные решения и продуктовые контракты редактируются вручную в той же задаче, где меняется соответствующее поведение. Если фактический блок устарел, `-Check` завершится ошибкой.
